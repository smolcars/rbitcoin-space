# Frontend

How the Solid 2 app in `web/` is put together (solid-js and @solidjs/web 2.0.0-rc.21, @solidjs/router 2.0.0-next.44, @solidjs/vite-plugin 3.0.0-next.57: pre-releases, pinned exactly), and the rules that let several people build pages at once without colliding. The visual rules are in [`DESIGN.md`](DESIGN.md); this file is about code.

## Layout

```text

  .oxfmtrc.json         Formatter settings

  index.html            The shell document: preloads the font, runs public/boot.js, loads src/index.tsx
```

## Routing

`@solidjs/router`. `index.tsx` makes the router with `createRouter({ routes, scrollRestoration: false })` (the browser restores scroll on back and forward) and renders the shell as its render-prop child. Mainnet pages are at the root and the other networks under `/signet`, `/testnet4`, `/testnet5` and `/regtest`, matching the server ([`ARCHITECTURE.md`](ARCHITECTURE.md)). `src/routes.ts` mounts every page's routes under all four prefixes, so a page is written once with network-free paths (`/tx/:txid`) and works on every network. The server sends the app shell for any page path, so deep links and reloads work; a disabled network's paths are a 404 from the server.

The network comes from the path. `useNetwork()` returns it; never keep it anywhere else.

Every page is loaded lazily.

### Adding a page or a route

1. Create `pages/<page>/` with `<Name>Page.tsx` (default export) and `routes.ts`:

   ```ts
   export const routes: RouteDefinition[] = [
     { path: "/blocks", component: lazy(() => import("./BlocksPage")) },
   ];
   ```

2. Spread `routes` into the list in `src/routes.ts`, before `notFound`. That one line is the only edit outside your directory.

Sub-pages (`/mining/pool/:slug`) go in the same `routes.ts`; you never touch `src/routes.ts` again.

### Links

Internal links stay on the current network. Use `<Link href={paths.tx(txid)}>` from `components/Link.tsx`; it adds the prefix and the router handles the click. The router handles every same-origin `<a>` and marks the ones that match the location: `aria-current="page"` on an exact match (it never touches an `aria-current` you set) and `data-active` on a match by path. Give an in-page `#` link `rel="external"`, as the skip link has, so the browser scrolls to it and it is not announced as the current page. Build every path with `paths` in `lib/network.ts`, which encodes chain data into a single path segment so it can never change the route or the scheme ([`SECURITY.md`](SECURITY.md) rule 14). Add a function to `paths` for a new page rather than writing the path by hand. To navigate from code: `navigate(onNetwork(network(), paths.block(h)))`.

### Page title

Call `usePageTitle(() => "Block 975 411")`. Test networks get their name in front, and every title ends in `| rbitcoin.space`.

### Link previews

A chat app or site that a link is pasted into fetches the page and reads its head without running any script. So the server fills in the shell's head per path (`crates/server/src/pages.rs`): it replaces the build's `<title>` element with the page's title and a one-line description, as `<title>`, `<meta name="description">`, `og:title`, `og:description`, `og:type` (`website`), `og:site_name` and `twitter:card`. With `SITE_URL` set ([`CONFIG.md`](CONFIG.md#site-address)) it adds a picture card: `og:url`, `og:image` with its type, size and alt text, `twitter:card` `summary_large_image` and `twitter:image`; without it, `twitter:card` is `summary` and nothing names an absolute address. Those are the names Open Graph readers (most chat apps) and summary-card readers look for. Every other byte of the shell is the build's, and the app replaces the title as it does on any load.

- **The wording is in two places, held equal by a test.** A page's title comes from its own `usePageTitle` call; the server's table in `pages.rs` writes the same title for each page kind, and `e2e/preview.e2e.ts` loads every page with the served title blanked and checks the page sets back exactly the server's. Change a page's title and that test fails until `pages.rs` says the same. The descriptions are the server's alone.
- **Nothing is asked of the node for a head.** A description uses the path's parsed identifier, the network, and what the server already holds: a block's time, miner, transaction count and fees from the block table, and a Lightning node's alias, channels and capacity from the graph in memory. A block by hash the table does not hold is named by its hash, as its page is until it loads; past two table reads at once, server-wide, a block's head goes without its facts.
- **Identifiers are parsed, then escaped.** Each is parsed into its type with the API's own parsers (a txid or block hash is 64 hex digits, a height 1 to 10 digits within `u32`, an address parsed for the network or a public key in its place (then the title says Public key), a Lightning key 66 hex digits, a channel id in its canonical forms, a pool slug the pool list knows) and only that value is written, through an HTML escaper. A path that does not parse gets the shell as built. An alias is cleaned as `cleanAlias` cleans it (control and format characters to U+FFFD, stacked marks thinned, with tables in `pages.rs` generated from the JavaScript engine's own `\p{Cf}` and `\p{M}` (Unicode 17.0)), then escaped; with no name left the title uses the key's first 20 digits, as the page does. The rankings page's `by` is read decoded, first one only, as `URLSearchParams` reads it.
- **Absolute addresses come from `SITE_URL` alone,** never from `Host`, which a client chooses. `og:url` is that address and the request's path, escaped; the query is left out, but for the rankings page's order, written back as `?by=channels` or `?by=age`. There is no canonical link.
- **The site's picture for most pages:** `web/public/assets/preview-<hash>.png`, 1200 by 630, drawn from `design/preview/card.html` (its header says how to redraw it with headless Chromium). The build copies it to `/assets` unchanged, so it has `/assets`' year-long cache. Chat apps keep a picture by its address for a long time, so a redrawn one needs a new name: the name is the first 8 hex digits of the file's SHA-256, `IMAGE` in `pages.rs` names it, and a test fails until the two agree. Keep it under 300 KB, as some apps skip larger pictures.
- **A transaction's and a block's own card.** Their pages' `og:image` and `twitter:image` name a picture of the page's figures, with alt text in our words and the parsed id: `{network}/app/card/tx/{txid}.png` and `{network}/app/card/block/{height or hash}.png`, written from the id as parsed (lower-case hex, a height without leading zeros), never from the request's path. Under `/app`, where no page lives, on every network. The card route parses the id as the page does; anything else, `.png` missing included, is a plain 404.
  - **What it shows** (`crates/card`, the mock-ups' direction C): the logo, the network, the kind and short id; the amount in BTC (outputs summed) or the height and its time as large as fits; then fee rate, fee, size and the date with "Confirmed", or the time it was drawn (UTC) with "Unconfirmed", since a chat app keeps a picture for days; or the miner (a name from our pool list only), transactions, median fee and fees. Under them the home page's strip with the subject's block ringed, and a transaction's marker in its fee colour. Only numbers, ids and fixed words are drawn, never text from a transaction or a coinbase. The big figure and the row shrink, whole, until they fit inside the margins, so no amount or count is cut.
  - **The strip.** With the mempool engine on and the subject unconfirmed or among the newest four blocks: three projected blocks, the tip's line, the newest five. A block further down, or any card on a network whose engine is off: the newest eight after the tip's line while the subject is among the first seven, else the subject with three newer and four older neighbours and no line. The strip's last tile runs off the card's edge, so the subject is never in it. An unconfirmed transaction is ringed (dashed) in its projected block; past the first three, its own block takes the third tile, labelled with its wait (`~60 min`); without a projection it is not ringed. At the tip, a block whose fee rates the table lacks for a moment is an empty tile.
  - **What one costs** (`crates/server/src/cards.rs`). A transaction the mempool tracker holds: two read locks taken briefly on a blocking thread, and one block-table read. Any other transaction: one Esplora `/tx/{txid}` read, shared with identical reads in flight, and one table read. A block: two table reads and no node call; a block the table does not hold gets the site's picture. Requests for the same card share one build. Two cards are built at once server-wide, each given 3 s for its reads, then drawn on a blocking thread in about 20 ms (release build) into a PNG of about 60 KB.
  - **A link never loses its picture.** A transaction the node does not know, a node that fails or takes longer than 3 s, a block the table does not hold, a strip away from the tip with a block that has no fee rates (older than the rates the table keeps, a year by default, or still waiting for the backfill; [`STORE.md`](STORE.md#blocks)), and both cards' slots taken: each answers the site's picture, `200` with `Cache-Control: public, max-age=60`. A client past its own `/app` allowance is refused before any of this, as on every route ([`SECURITY.md`](SECURITY.md) rule 7).
  - **Caching.** A drawn card is kept in memory, at most 4 MB, the least recently used dropped first, for as long as its `Cache-Control` says: a day (`public, max-age=86400`) once its block is 100 deep, past any reorg, and every block it draws has its fee rates, so only a new pool list changes it; a minute for an unconfirmed transaction and for a block nearer the tip, whose strip moves with each block.
  - **The font.** The cards are drawn in the site's Recursive Mono at 400 and 600, from two static TrueType subsets in `crates/card/fonts/` (17 KB each, printable ASCII, the ellipsis, the en dash and the narrow no-break space, with the slashed zero as the zero), made from `design/fonts/recursive.woff2` by `design/fonts/card-subset.py`, its licence beside them. A test fails if a pool name or any word a card writes has a character the subset lacks; the pick and lightning bolt in one pool's name are drawn as shapes of our own. Pictures of every state, extremes included, are in `fixtures/cards/`, compared pixel by pixel (`CARD_FIXTURES=write cargo test -p card` writes them again after a deliberate change).
- **Caching.** Pages are `Cache-Control: no-cache`, as the shell was: the head depends on the URL alone, which every cache keys on, so no cache shows one page's head on another, and a deploy shows at once. The shell is read once at start and templated per request in microseconds; a new frontend means a restart, which a new image is. Pages are not sent precompressed any more: the shell is about 1.3 KB.

## Data

### The public API

`lib/api.ts` is the only way pages talk to `/api`. Paths are relative to the network's API, so the same code works on every network.

```tsx
const params = useParams<{ id: string }>();
const [block] = createApi<Block>(() => `/block/${encodeURIComponent(params.id)}`);

<Show when={block()} fallback={<Loading label="Loading block" />}>
  {(b) => <h1>Block {groupDigits(b().height)}</h1>}
</Show>
```

- `createApi<T>(path, { as: "text" })` returns `[request, { refetch }]`. `request()` is the answer: undefined before the first, the last one while it asks again, and it throws once the last attempt failed, so read `request.state` (`unresolved`, `pending`, `ready`, `refreshing`, `errored`) first where a failure is expected; `request.error`, `request.loading` and `request.latest` are there too. It asks again when the path or the network changes, aborts the request it replaces and the one in flight when the page unmounts, answers from the cache without a network request, and stays loading while a busy refusal waits to be retried. Return a falsy path to wait for something else first. With `{ fresh: true }` every answer comes from the server, never from the browser's HTTP cache, for a request a live message prompted ([Following live data](#following-live-data)); without it, `refetch` of the same path is fresh and a first ask may come from the cache. `createRequest(source, (source, signal) => …)` is the same for a fetcher of your own (the block page's summary and transaction records).
- `fetchApi<T>(network, path, { as, signal, fresh })` is the same call as a promise, for event handlers and loops. `fetchApp<T>` is the same for the app's own API under the network's `/app`.
- **Chain-tip stamps.** `createApi<T>(path, { stamped: true })` and `fetchStamped<T>(network, path)` give `{ value, tip }`, where `tip` is the `X-Bitcoin-Chain-Tip` and its height that the reply is as of (undefined for an unstamped or cached reply). Take every figure that depends on the tip from one stamped reply, or compare the stamps of two: the block page counts confirmations from its status reply's stamp, and the home page's difficulty panel asks again while its answer's stamp trails the strip's tip.
- **Busy servers.** Every call above retries a 503 or 429 by itself, no sooner than its `Retry-After` (kept on `ApiError.retryAfter`), backing off from 1 to 30 s with a little jitter, six times, then rejects with the last error. They are all GETs, safe to repeat. Five 503s are not retried, because a retry cannot change them: an address too large to total, an address index that is off ([`API.md`](API.md#error-bodies-are-ours)), mining history on a server without a block table ([`API.md`](API.md#mining)), mempool history on a server without a data directory ([below](#mempool-history)), and the relatives and replacements routes (`/app`'s and `/api/v1`'s) on a network whose mempool engine is switched off. Show a loading state, not an error, while a call is pending. `withRetry(call, signal)` is the loop itself, for a call that does not go through `api.ts`; only wrap a call that is safe to repeat. A refusal it already gave up on is never retried by a loop around it. The browser still logs each refused request to the console; browser tests that may meet one allow `/status of (429|503)/`.
- **Coverage.** A history answer (the mining routes) says how far back its data reaches in `X-Data-From-Height`, `X-Data-From-Time` and `X-Data-Complete` ([`API.md`](API.md#coverage)). A stamped reply carries them as `coverage: { fromHeight, fromTime, complete }` when sent (`readCoverage` reads them). Say "data from … onward" where `complete` is false; never draw the missing stretch as zero.
- `as: "text"` reads plain-text replies (`/blocks/tip/height`, `/block-height/:h`, `/tx/:txid/hex`), and `as: "bytes"` binary ones as an `ArrayBuffer` (`fetchApp(n, "/block/<hash>/txs", { as: "bytes" })`). The default is JSON.
- Failures are `ApiError` with `status` (0 when the server cannot be reached, with a message that says so when the browser is offline) and a message fit to show. `isNotFound(e)` tests for 404. An abort is passed through as the abort error, not as an `ApiError`.
- Replies the server marks as never changing (`immutable`, or `max-age` of a day or more) are kept in memory, at most 256, for the life of the page. Everything else is fetched every time and left to the browser's HTTP cache.
- A request never suspends: the page frame shows at once and each section fills from `state` as its data arrives. Pages do not use Solid 2's async memos (`createMemo` returning a promise): read inside the shell's `<Loading>`, one would hold the whole page until it loads. The shell's `<Loading>` waits only for a page's code.
- An error thrown while rendering reaches the shell's `<Errored>` boundary, which shows "This page could not be shown". Catch expected failures (not found, node unavailable) in the page with `<ErrorState>` instead.

### When a page's files fail to load

Every page, and the transaction grid, is a chunk of code with its own stylesheet, downloaded on first use. A download can fail: a dropped connection, a busy proxy, or a deploy that replaced the files while a tab was open. Vite never asks for a failed stylesheet again by itself, so `lib/chunks.ts` notes every `<link rel="stylesheet">` and `<link rel="modulepreload">` (Vite preloads a page's code and its imports with one) that fails (`watchFiles`, started in `index.tsx`), and `retryFiles()` asks for each stylesheet again through a fresh `<link>` and for each script with a request that skips the cache, which proves it downloads now. A part of the page that loads its own code (the palette) passes `retryFiles` a test of the address and is asked only for its own files: a page's failed files stay on the list for the shell, which is waiting to ask for them. The script itself is loaded again when its `import()` runs again, which the router's `lazy()` does on the next render. WebKit never does: once a script's preload or import failed, it answers every later `import()` of that script, and of any module that imports it, with the same failure and no request, for the life of the document (Playwright's WebKit 2370, checked against a 503 from a real server). Chromium and Firefox ask again.

The shell's `<Errored>` boundary handles both. On a chunk error it shows "Loading this page" and tries again after 1, 2 and 4 s: before each attempt it asks `/app/config` (never from a cache) whether the server's version changed since the tab loaded, then asks again for the failed files, and renders the page again only once they are in, so a page never appears unstyled. If the page fails to load again within 2 s of an attempt that proved its scripts download, the browser is holding on to the failure, and the page reloads (`reloadOnce`): that is how WebKit recovers. It reloads at most once a minute per tab, kept in session storage, so a file that downloads but never runs cannot loop; without session storage it does not reload, and the reader gets "Try again" as before. When the attempts run out it says that part of the page could not be downloaded, with "Try again", which asks for everything again. When the version changed, the files this tab needs were replaced by a deploy: it says the site has been updated and offers "Reload" rather than retrying files that are gone. A navigation starts the count afresh.

`lib/esplora.ts` has hand-written types for the replies pages use, from rbitcoin v0.9.2's `docs/esplora-openapi.yaml`. Add a type when you use a new route; keep the field names exactly as the API sends them. Amounts are integer sats and times are unix seconds throughout.

During development, `bun run dev` proxies `/api`, `/app` and `/healthz` to the Rust server at `LISTEN_ADDR`.

### The app's own API

`GET /app/config` answers `{"networks": ["mainnet", "signet"], "version": "0.4.0", "ark": {"signet": ["bark"]}, "lightning": ["mainnet"], "broadcast": true}`: the enabled networks in server order, the server version, the Ark implementations of each network that has one ([`ARK.md`](ARK.md)), the networks whose operator switched Lightning on ([`CONFIG.md`](CONFIG.md#lightning)), and whether the server broadcasts (`BROADCAST_ENABLED`). The header shows Ark and Lightning only on those, and neither before the answer arrives; a Lightning address typed on another network still gets the page's "switched off". `loadConfig()` in `lib/config.ts` is the answer as the tab first read it, for pages that need it. It is server-wide, so it is served at the root only, whichever networks are enabled (`crates/server/src/app_config.rs`). The shell reads it once for the network switch and the footer. If the root's network (mainnet) is disabled, the shell moves to the same page on the first enabled network.

#### Block summaries

What the public API cannot give cheaply: a mined block's fee facts and every transaction's fee and size. Per network, under its `/app` (`crates/server/src/summary.rs`).

| Route | Answer |
|---|---|
| `GET /app/block/:hash/summary` | The block's facts, JSON (below) |
| `GET /app/block/:hash/txs?v=2` | Every transaction as a fixed-width binary record (below) |
| `GET /app/blocks/summary?hashes=<hash>,<hash>,…` | 1 to 10 blocks' facts, a JSON array in the order asked. Repeats are allowed |

```json
{
  "id": "00000000000000000000e13ad5e424f6ba7208b0c1a9a687e9ccc4d62b3b094c", "height": 975511,
  "tx_count": 4198, "fees": 1475029, "vsize": 999391, "weight": 3991349,
  "fee_rate": {"min": 0.10071942446043165, "p10": 0.12, "p25": 0.12698412698412698,
    "median": 1.0850888512305468, "p75": 2.007012551450785, "p90": 3.150749063670412, "max": 62.10091743119266},
  "fee_bands": [301870, 52011, 13132, 9447, 153, 5069, 233233, 20986, 238267, 102460, 17310, 5453],
  "miner": {"name": "Foundry USA", "slug": "foundryusa"}, "sv2": false,
  "audit": {"match_rate": 99.87, "expected": {"txs": 3100, "vsize": 998000, "weight": 3991200, "fees": 1500000}, …}
}
```

- `tx_count` counts every transaction. Everything else leaves the coinbase out, as `getblockstats` does: `fees` in sats, `vsize` and `weight` summed over the paying transactions.
- `fee_rate` is in sat/vB, unrounded, `null` for a block holding only its coinbase. Percentiles are weighted by virtual size: `p25` is the rate of the transaction where the cheapest quarter of the block's vbytes ends. Print them with `formatFeeRate`.
- `miner` is who mined the block, by the pool list's rules ([`API.md`](API.md#who-mined-a-block)): a listed tag first, then a payout to a listed address, else `{"name": "Unknown", "slug": "unknown"}`. `name` is the list's spelling and `slug` its pool page (`paths.pool`); a coinbase tag only selects one of the list's names and is never itself the answer. It comes from the stored row's coinbase, or from the coinbase the summary's block listing already reads, so it costs no extra node call and a server without a block table names miners too. A server older than this field leaves it out: say the miner is not known.
- `sv2` is `true` when the block's coinbase script is laid out exactly as the Stratum V2 reference implementation writes it ([`API.md`](API.md#who-mined-a-block), "Stratum V2 tags"), whoever `miner` names. It is a claim, like any coinbase tag: whoever built the block wrote those bytes, and nothing on the chain proves the protocol that was spoken. Only the boolean is served, never the tag's text. It is read from the same coinbase as `miner`: the stored row keeps the whole script, so it needs no column. A server older than this field leaves it out: treat that as `false`.
- `audit` is the block's health: its audit's totals ([Block audits](#block-audits) below), or `null` when it has none. A new block's summary is computed with its audit, so the `summary` message and the first fetch already carry it; `null` stays `null`. A server older than this field leaves it out: treat that as `null`.
- `fee_bands` is the virtual size paying in each of the twelve design bands, cheapest first: the strata. A block stored before the lowest band was split carries ten, all under 0.2 sat/vB in the first; `widenBands` (`lib/format.ts`) reads either, and the strata name that first band "under 0.20 sat/vB" ([`DESIGN.md`](DESIGN.md#fee-scale)). They sum to `vsize`. Each transaction is banded on its rate as printed, as `feeBand` does, so a stratum's color agrees with the numbers beside it. How full the block is comes from the block's own `weight` (Esplora) over 4,000,000.

`/txs` is `application/octet-stream`, little-endian: an 8-byte header, then one 28-byte record per transaction in block order, the coinbase first.

| Offset | Size | Field |
|---|---|---|
| 0 | `u32` | Format version, `2` |
| 4 | `u32` | Record count, `tx_count` |
| 8 + 28·i | `u32` | Virtual size of transaction `i` |
| 12 + 28·i | `u64` | Fee in sats; 0 for the coinbase |
| 20 + 28·i | `u64` | Total output value in sats |
| 28 + 28·i | `u64` | The transaction's flags ([`API.md`](API.md#transaction-flags)), with CPFP (bits 16, 17) from its relatives in the block and replacement (bit 18) from the server's record; read by the [goggles](#goggles) |

Read it with a `DataView`; a fee or value here is below 2^53, so `Number(view.getBigUint64(o, true))` is exact. The flags are read as two 32-bit words by `readFlags` (`lib/flags.ts`), which drops bits from 53 up: the highest the server sets is 44, and a newer one's new bit must not stop the map. A record has no txid: when a square is hovered or clicked, ask `/api/block/:hash/txid/:index`, which is cached for good. Mainnet block 976,000, 4,003 transactions, is 112,092 bytes (80,068 in format 1, without flags); the proxy in front may compress it (the server itself does not). The facts are about 400 bytes. Check the version before reading; a different one means a newer server and a page that needs a reload.

**The format is in the URL.** An answer is cached for good under its URL, so a new format needs a new one: the page asks for `?v=2`, the format it reads, and no browser or proxy holding a format 1 answer under the plain path can hand it one. The plain path, and `?v=2`, both answer format 2; any other query is a `400`. A tab still running an older page asks the plain path: a cached format 1 answer it reads as before, a fresh one tells it to reload, and the reloaded page asks `?v=2`.

**In the frontend.** `lib/summary.ts` has the type, `isSummary`, and `fetchSummaries(network, hashes, signal)`, which asks for up to ten at a time with `withRetry` and keeps every summary it sees, fetched or pushed, for the life of the page (`knownSummary`). The home page asks for its ten tiles in one batch on first paint and then takes each new block's from the WebSocket, asking over HTTP only if the push has not come within 4 s. Older tiles, as the strip scrolls into the past, are asked for once it stops ([The block strip's past](#the-block-strips-past)). The blocks list (25 a page, from three of the API's ten-block answers) asks per row, two at a time, so an old page fills in row by row. Draw the bands with `Strata`, and the records with the transaction grid below. The home strip's and the mining page's tiles put `miner.name` on the line under each tile (`aria-hidden`, its space always kept) and in the tile link's text; the block page links it to the pool's page. A block with `sv2` carries the Stratum V2 mark after its miner's name in the blocks list and on the block page ([`DESIGN.md`](DESIGN.md#block)), and nowhere else: a tile's pool line is one fixed line. Its class, `block-sv2`, is in `pages/block/parts.css`, which the two pages share.

**Caching.** A summary's transactions are fixed by its hash (all but bit 18 of their flags, which is the replacement record when it was computed), so `/txs` success is `Cache-Control: public, max-age=31536000, immutable`. The facts are not: their miner and audit come from our store, and a release with a new pool list names a miner differently, so they are `public, max-age=86400`. A release that adds a field (`sv2`) is the same case: the server keeps nothing across a restart, but a browser holding an older answer reads the field as absent: from its HTTP cache for up to a day, and in a page already open for as long as the page holds that answer in memory, at most until it is reloaded. Both are long enough for `api.ts`-style in-memory caching for the life of the page. Errors are `no-store`.

**Cost and limits.** A block in the block table with its fee rates ([`STORE.md`](STORE.md#blocks)) costs nothing: once backfilled, the facts of the last year's blocks come from there. `/txs` always needs the node. An uncached block costs the node a block listing: about 60 ms and 0.3 MB on mainnet where the node has the listing route, a heavy call (about 0.7 s and 10 MB) where it does not ([`RBITCOIN.md`](RBITCOIN.md#listing-a-blocks-transactions)), and beside it the raw block for the flags (up to 4 MB, [`RBITCOIN.md`](RBITCOIN.md#listing-a-blocks-transactions)), so:

- Concurrent requests for one block share one computation, and the facts and the records come from the same one.
- The newest ten blocks are computed as they arrive, so the home page's tiles are always cached. A new block's facts are also pushed on the WebSocket as a `summary` message; use that rather than fetching.
- Each network computes one block at a time, and holds at most six started by clients. Past that the answer is `503` with `Retry-After: 1`. Retry: the work already admitted goes on, so a retry finds more of it cached. A cold batch of ten needs a retry or two.
- Each client may start ten computations at once, then one every 2 s; past that `429` with `Retry-After: 2`. Cached blocks never count. A page walking back through history should fetch tiles lazily, as they scroll into view.
- `404` is an unknown block, `400` a malformed hash or query, `502` and `504` the node failing. All are worth a "Try again".

#### Block audits

How a block compared with the block we expected on its parent, for the block page's expected-against-mined view and a tile's health. The method and the meaning of each category are in [`MEMPOOL.md`](MEMPOOL.md#block-audits); read it before labelling anything. Per network, under its `/app` (`crates/server/src/audits.rs`).

| Route | Answer |
|---|---|
| `GET /app/block/:hash/audit` | The whole audit, JSON (below). `404` when the block has none, `503` on a server without a block table |

The totals, the same object as the facts' `audit` (which leaves out `id`, `height`, `time`, `seen_at`, `txs` and `complete`):

```json
{
  "id": "…", "height": 975540, "time": 1794480000, "seen_at": 1794480003,
  "match_rate": 99.87,
  "expected": {"txs": 3100, "vsize": 998000, "weight": 3991200, "fees": 1500000},
  "actual": {"txs": 3150, "vsize": 997500, "weight": 3990000, "fees": 1498000},
  "matched": {"txs": 2900, "vsize": 950000},
  "missing": {"txs": 3, "vsize": 1200}, "displaced": {"txs": 40, "vsize": 9000},
  "fresh": {"txs": 150, "vsize": 35000}, "conflicted": {"txs": 7, "vsize": 2000},
  "added": {"txs": 60, "vsize": 9500}, "unseen": {"txs": 1, "vsize": 200},
  "txs": [{"txid": "…", "kind": "missing", "vsize": 400, "rate": 1250, "first_seen": 1794479000}],
  "complete": true
}
```

- `match_rate` is percent with two decimals, rounded down: 100 means nothing was left out without an innocent cause. Only `missing` lowers it. Print it as is; do not round it up.
- `expected` is our first projected block on the parent; `actual` the mined block without its coinbase. `vsize` is sigop-adjusted on the expected side and `ceil(weight / 4)` on the mined side, so the two can differ by a little for the same transactions. Fees in sats.
- Each category is `{txs, vsize}`. `matched` + `missing` + `displaced` + `fresh` + `conflicted` is the expected block; `matched` + `added` + `unseen` the mined one.
- `txs` lists every transaction in a category other than `matched`, the most telling first (`missing`, `unseen`, `added`, `displaced`, `conflicted`, `fresh`), highest rate first within each, at most 1,000. `complete` is `false` when that cap cut the list. `kind` is the category. `rate` is sat per 1,000 vB: the rate we placed it at for the expected kinds, its own fee over its size for `added` and `unseen`. `first_seen` (Unix seconds) is our node's accept time, present only for expected kinds still in our mempool after the block. Matched transactions are not listed: draw them from the block's own records (`/txs`) and the txids from `/api/block/:hash/txids`.
- No audit is a state to show, not an error: "not audited: this server was not watching when it was mined" (or the projection was stale). It never appears later.

**In the frontend** (`components/audit/`). `model.ts` reads the totals with `readAudit(summary.audit)`, which gives `null` for `null`, a missing field (an older server) or a shape it cannot draw, and the detail route with `readAuditDetail`, which drops entries it cannot read. It also holds each category's name and plain-words meaning (`CATEGORIES`), the same words as [`MEMPOOL.md`](MEMPOOL.md#categories): use them wherever a category is named. `formatMatchRate` prints the score as sent, two decimals, never rounded up.

- **The block page** shows `AuditSection` below the map and facts, from the summary it already has: the match rate, the expected block against the mined one (transactions, virtual size, fees), the two laid side by side with their matched parts lined up, and every category with its count and size ("None" when empty) and what it means; on a phone the meanings wait behind one "What each kind means" button, the counts in sight. Without an audit it says so in one muted line, with no figures. A new block's facts can reach the page over the WebSocket before its own request answers, so while the facts are on their way the page listens to `blocks` and takes a `summary` for its block from there.
- **The list** (`AuditList.tsx`) is a lazy chunk, fetched with `/app/block/:hash/audit` only when the reader asks. It shows one category at a time, the server's most telling first, each transaction linked to its page, and says when the server cut it at 1,000 and how many of a category it lists.
- **The blocks list** has a "Match rate, %" column, blank for a block without an audit, on wide screens; a phone keeps the miner and the transaction count instead.
- **The blocks list's "Time to mine"** is a block's header time less its parent's, so it can be negative and says so ("−2 min 5 s"). The page asks for one block past its 25 so the oldest row has its parent; block 0 shows a dash. Phones drop it. Its bar and notes are in [`DESIGN.md`](DESIGN.md#time); the home strip's tile gives the same note on its time when the strip holds the tile's parent.
- **The mining page's block health** (`pages/mining/Health.tsx`, the "Match rate" tab of the block charts) charts each audited block's match rate over the page's period, from the public `/api/v1/mining/blocks/predictions/:interval`, on an axis from 0 to 100%, so a block that matched badly is a notch down from the top. A block without an audit between two that have one is a gap, never a line drawn across it, however long miners took; past 1,000 blocks in the period a point is the lowest of a run of blocks, so a bad one still shows, and opens that one; a run missing a block breaks the line after it, and its readout says how many of the run were audited. The route says nothing of coverage, so the page says it from the answer: one short line over the chart gives their share of the period's blocks (the pools' count, only when that answer covers the whole period: a history still filling in counts fewer) and the first one's time, and the period before it is hatched. A point opens its block: a click, a second tap on the point a finger picked, or Enter on the focused chart; its row in the figures links there too.
- **Past difficulty adjustments** (`pages/mining/Adjustments.tsx`) list `/api/v1/mining/difficulty-adjustments` newest first, the latest six and then all of them a press away (mainnet has about 480, so one list, not pages). The next adjustment's expected change, from `/api/v1/difficulty-adjustment`, is a figure in the band at the top of the page, with the latest past change under the difficulty. A change reads as an arrow and a word ("↑ Up 5.54%"), as the home page's does; each row opens the block that began the period. They do not follow the period: they are every retarget stored. Regtest's list is empty and says the network never adjusts.
- **The grid is not tinted by category.** Its records have no txids, so marking audited transactions would mean fetching every txid of the block, and color in the grid carries fee and nothing else ([`DESIGN.md`](DESIGN.md#principles)). The list is the way in.

**Caching.** An audit is fixed once written: success is immutable, and a `404` is `no-store` but final in practice.

**Cost.** One indexed read, no node call, kept in memory until the next write to the audits or the block table ([`API.md`](API.md#answers-kept-in-memory)); at most about 60 KB of JSON for a capped list.

#### A transaction's relatives and replacements

For the transaction page: who it will be mined with, what replaced what, and what changed between two versions. Per network, under its `/app` (`crates/server/src/relatives.rs`, `crates/server/src/replacements.rs`, `crates/server/src/compare.rs`). They answer from the server's memory (the compare route asks the node only in the one case below), so they are cheap and need no caps beyond the ordinary request limits. All are `Cache-Control: no-store`: the mempool moves.

| Route | Answer |
|---|---|
| `GET /app/tx/:txid/relatives` | A mempool transaction's cluster, its chunks and its parents and children (below) |
| `GET /app/tx/:txid/replacements` | What this transaction replaced and what replaced it, as far as the server remembers (below) |
| `GET /app/tx/:txid/compare/:other` | Two versions of one replaced transaction side by side: figures, inputs and outputs (below) |

**Relatives.** The cluster is the node's own (`getmempoolcluster`), as the projected blocks last asked for it: at most one mempool update behind. Which member spends which is read from the transactions' inputs.

```json
{"txid":"<parent>","stale":false,"chunk":0,
 "parents":[],"children":["<child>"],
 "chunks":[{"fee":3314,"vsize":265,"rate":12505,"txs":["<parent>","<child>"]}],
 "txs":[{"txid":"<parent>","chunk":0,"time":1794467650,"fee":139,"vsize":139,"block":0,"parents":[]},
        {"txid":"<child>","chunk":0,"time":1794467650,"fee":3175,"vsize":126,"block":0,"parents":["<parent>"]}]}
```

- `chunks` are the cluster's mining chunks in the node's order, best first; `chunk` is the index of the one holding this transaction. A chunk is mined whole, at its `rate`: that is the "effective fee rate" (CPFP). `fee` is the node's chunk fee, `prioritisetransaction` included; `vsize` is the chunk's sigop-adjusted size. A chunk can count a member the server has not seen yet, in the moment after it arrived, so `fee` and `vsize` can exceed the sum of `txs`.
- `txs` are the members in mining order with their own figures, the chunk they are in, their projected block (`null` before the projection places them) and their parents inside the cluster. `time`, `fee` and `vsize` are `null` for a member that left a moment ago.
- `parents` and `children` are this transaction's own unconfirmed ones. Their parents and children are in `txs`: draw the graph from there. A cluster holds at most 64 transactions.
- `404` `{"error":"not in the mempool"}`; `503` with `Retry-After: 1` for `mempool is syncing` (the server just started), `not placed yet` (it arrived a moment ago) or `mempool is switched off` (no retry will help); `400` for a malformed txid.

**Replacements.** A bounded record per network: the most recent `REPLACEMENTS_KEPT` (10,000) replacements, oldest out first, kept in memory and, with a `DATA_DIR`, in the store, so it survives a restart ([`MEMPOOL.md`](MEMPOOL.md#following-a-transaction)). Someone who opens a replaced transaction's page later still learns what replaced it.

```json
{"txid":"<B>","truncated":false,
 "replaced_by":[{"txid":"<B>","by":"<C>","seen":1794467700,"fee":695,"vsize":139,"rate":5000,"by_fee":2000,"by_vsize":139,"by_rate":14388,"shared_inputs":1}],
 "replaces":[{"txid":"<A>","by":"<B>","seen":1794467643,"fee":139,"vsize":139,"rate":1000,"by_fee":695,"by_vsize":139,"by_rate":5000,"shared_inputs":1}],
 "versions":["<A>","<B>","<C>"],"versions_truncated":false}
```

- `replaced_by` follows this transaction forward to the newest replacement known, oldest link first. The last link's `by` is the one to show.
- `replaces` walks backward: what this one replaced, and what those replaced, newest first. A replacement can replace several transactions at once (a transaction and its children: a child leaves with its replaced parent and carries the same replacement).
- Each link: `seen` is when the server saw it (Unix seconds); `fee`, `vsize` and `rate` are the replaced transaction's own, `by_*` the replacement's, `null` when the replacement was confirmed in the block that removed the original. `shared_inputs` is how many inputs the two share, `null` when not recorded; `0` means the replaced transaction was a child that left with its replaced parent, not an earlier version. At most 32 links each way; `truncated` says there were more.
- `versions` is the line of versions this transaction belongs to, oldest first, this one among them: those joined to it by version links only, never through a child's link ([`MEMPOOL.md`](MEMPOOL.md#following-a-transaction), "Versions"). Empty when it has no other version. At most 33; `versions_truncated` says there were more.
- Empty lists mean the server saw no replacement since it started, not that there was none. `503` with the mempool engine switched off; `400` for a malformed txid.

**Compare.** Two versions of one transaction, `a` the first named and `b` the second, in any order, neighbours or not: they must be versions of one another, joined by version links only, so a child that left with its replaced parent is never compared ([`MEMPOOL.md`](MEMPOOL.md#following-a-transaction), "Versions").

```json
{"shared_inputs":1,
 "a":{"txid":"<A>","fee":500,"vsize":200,"weight":800,"value":1000,"rate":2500,"inputs":2,"from":"record",
      "outputs":{"state":"kept","list":[{"value":1000,"script":"0014…","address":"bc1q…"}]}},
 "b":{"txid":"<B>","fee":1000,"vsize":250,"weight":1000,"value":2001,"rate":4000,"inputs":1,"from":"mempool",
      "outputs":{"state":"kept","list":[{"value":1000,"script":"0014…","address":"bc1q…"},
                                       {"value":1001,"script_len":83,"script_hash":"<32 hex>"}]}}}
```

- `outputs` is as kept while the version waited in the mempool ([`MEMPOOL.md`](MEMPOOL.md#outputs-kept-for-the-compare-view)): `kept` with each output's value (sats) and its script as hex with its `address` (`null` for a script without one), or for a script over 34 bytes its length and the first 16 bytes of its SHA-256 as hex; `too_many` with `count` past 32 outputs; `not_recorded` when the server has none (a link stored before outputs were kept, a version the tracker held past its budget, or one the node has forgotten). Scripts are attacker-controlled bytes: show them as text.
- `inputs` is the version's input count, `null` when not recorded or when the node's reply lists only some inputs (pruned). `shared_inputs` is how many inputs both spend, when one directly replaced the other and the tracker held both or the block holding the replacement shows it, else `null`.
- `vsize_basis` is `sigops` when both sizes are the tracker's, adjusted for signature operations, and `weight` when either side came from the node, whose size is weight over four: both sides are then put on weight, so a change in `vsize` or `rate` is never only a change of basis.
- `from` says where the version came from: `record`, `mempool` (still waiting, from the tracker), `node`, or `none` when nothing is known of it but its txid. Figures are `null` when unknown.
- **The one node read:** a version with no outputs in the record or the tracker that was not itself replaced (the newest of its line: confirmed, or a replacement confirmed straight from a block) is asked of the node's Esplora (`/tx/:txid`), which still has it: one read, through the same coalescing as the public transaction route, so identical requests in flight share it; at most two a request, and none for a txid that is not a version of the other. A version that was itself replaced is never asked: the node forgot it. The node's figures fill only what the record lacks. More than 32 outputs are counted before any script is read.
- `404` `{"error":"not two versions of one transaction"}`; `400` for a malformed txid or the same one twice; `503` with the mempool engine switched off.

**In the frontend** (`lib/compare.ts`, `pages/tx/Compare.tsx`): `parseComparison` reads the answer strictly (an `address` that is not plain letters and digits is dropped); `matchOutputs` pairs the newer version's outputs with the older's by script, the same amount first so a repeated destination keeps its unchanged output, then the rest in order, and calls each kept, changed (with the difference), added or removed. The line of versions is the server's (`versions` on `/app/tx/:txid/replacements`): the page never works one out, so a child's link is never taken for a version's, and nothing is offered for comparison until the route has answered. The page asks the route again when the `tx:` topic says the transaction was replaced, and again when its newest replacement changes, since the topic's links do not say whether a link is a child's. The replaced version's notice compares it with what replaced it (or, when it left as a child, with the version before it in its own line, under a line saying it left with a replaced parent); each chain link between two versions has a button, and the From and To pickers list the line; buttons and pickers set one pair held by the chain. A version that replaced others compares itself with the one before. **A child's page never says it was replaced.** A link is a child's when the route says the two share no input (`leftWithParent` in `pages/tx/Live.tsx`, asked of the very link shown: its transaction and what the link names, so an answer about another link of the same transaction says nothing of this one). The page then says only what such a link proves: the transaction left the mempool when the named one replaced a transaction it depended on, the one it spent from or one further back. So the badge reads "Removed"; the notice is headed "Removed with a replaced transaction" and says "It left the mempool when … replaced a transaction it depended on. No new version of this transaction took its place. It can still confirm only if the replaced transaction is mined after all." (a miner that never saw the replacement can still mine the original, and the child with it); each line of the chain speaks for its own link ("removed when … replaced a transaction it depended on", or "replaced by …"); a chain with a child's link in it is never called a line of versions (no "It was replaced N times", and the link to follow is "the newest in this line"); the steps and the Replaceable fact say the same. The page remembers which links the route said are a child's, and nothing else of an old answer, and keeps them beside what the route says now for the links it no longer speaks of: when a later ask fails, or is answered after the server's bounded record has let the link go while the topic still shows it, the page does not go back to "Replaced" (and shows no comparison it cannot vouch for). The summary and the last step say "Not expected to confirm" for a child, not "Will not confirm". The topic's word comes first, a moment before the route's, and says only "replaced", which is announced; once the route answers, the page announces "Not replaced itself: it left the mempool with a transaction it depended on, which was replaced." When its line later goes on, by a new version or by another removal, it says only that the line changed, how long it is now and its newest end ("The line of transactions it left with changed: 3 links now, the newest 88888888."), a new sentence each time. Whatever the page announces, the same words twice in a row are said twice: a live region speaks only when its text changes, so a repeat carries a trailing no-break space, which is not read out. The page remembers at most 32 such links, the newest, and never forgets one it is showing. **A confirmed transaction always asks for its history**, however long ago it confirmed: the record keeps replacements by count, not by age, so no cutoff by depth could be exact. That is one request per confirmed transaction's page, answered from the server's memory, never the node: for a transaction with no replacement the answer is 165 bytes of JSON with 404 bytes of headers, in 0.13 ms of server time at the median and 0.25 ms at p99 (303 requests on regtest, 2026-11-18). A server without the mempool engine answers `503`, read as no history.

#### A confirmed transaction's fee verdict

Under a mined transaction's fee rate, one muted line says how its rate compares with the low end of its block: "At the low end", "Near the low end", or "33× the low end". It is a `Note` button: a tap, a key or the mouse opens the full sentence ("33 times its block's low end. The cheapest tenth of block 976 474, by size, paid 0.31 sat/vB or less. Compared with this transaction's own rate."), which screen readers hear as its description. It is information, never a warning: no colour and no icon. The code is `pages/tx/verdict.ts`.

- **The low end is the block's `p10`**, from its summary ([Block summaries](#block-summaries)): the own rate of the transaction where the cheapest tenth of the block's vbytes ends, so at least a tenth of the block's space paid that or less. Not `min`: it is one transaction's rate, often 0 or a few hundredths (a pool's own zero-fee transaction, a parent its child paid for). In mainnet blocks 976,468 to 976,477 `min` was 0 in four and under a tenth of `p10` in three more (976,471: `min` 0.15, `p10` 3.01). Neither is "what was needed": the words never say so.
- **Like with like.** The block's figures are each transaction's fee over its own vsize, so the page compares the transaction's own rate (its fee over its vsize). A mined transaction may have been mined for a package's rate, which the page does not know. So: a spend of its outputs in the same block (a child that may have paid for it, read from the outspends the page already has, or asked again when those were answered before it was mined) hides every verdict. A parent mined in the same block (one `GET /tx/:parent/status` per distinct parent, at most 8; past 8, neither is shown) hides "near" and the multiple, which a package's lower rate would make overstated. "At the low end" stands, whatever the number of parents, and asks about none: a package's rate would be lower still. An answer about a relative counts only when its chain-tip stamp (`X-Bitcoin-Chain-Tip-Height`) is at or above the block's height: the page's own outspends are used when theirs is and the transaction's own answer named this block (not another that held it at the same height before a reorg), and asked again otherwise; a parent's status is asked past the browser's cache; an answer below the block, or without a stamp, shows nothing. So spends answered a moment before the block, or a status a cache kept across a reorg, cannot stand as proof that no relative was mined in it. Chains of cheap transactions mined together are common, so many low-end transactions show nothing; that is intended.
- **Thresholds.** "At" when the rate, as printed, is no more than the low end as printed, so it never contradicts the two figures. The low end is printed rounded up (`0.013` reads `0.02`), so the note's "or less" is true of the figure it prints. A rate twice the low end or more is never "at", though rounding can make two very low rates print alike (`0.0249` against `0.0101`: both `0.02`, and "2.4×"). "Near" below twice the low end: one block's `p10` and the next's differed by more than 2× in five of the nine neighbouring pairs of mainnet blocks 976,468 to 976,477 (2.00, 1.70, 1.21, 3.01, 2.19, 1.00, 0.30, 0.01, 0.12, 0.12), so a smaller multiple says more about which block took it than about the fee. From 2× the multiple, rounded down so it never claims more: one decimal under 10 (`2.4×`), whole and grouped above (`335×`, `76 923×`).
- **Nothing is shown** for a coinbase, an unconfirmed transaction, a block whose summary is missing or failed (older than the stored range, `null` or `503`), a block without rates (only a coinbase), a low end of 0, or while any of it loads. The line's room is kept from the moment a verdict may come (a mined transaction that is not a coinbase), filled or not, so a verdict arriving moves nothing: at 1440 and 390 px the block cell beside it is as tall, and at 320 px, where the fee rate has a row to itself, the panel is 424 px before and after (measured with the summary and the outspends held back 1.5 s). There a transaction that gets no verdict keeps one empty line under its fee.
- **Cost:** the summary is one request that `fetchSummaries` keeps for the page's life (the block page and home tiles share it); then, only when it could show something, the parents' statuses. The page asks nothing for a coinbase or an unconfirmed transaction.

#### Mempool history

For the mempool chart: the mempool's size by fee band through the day, the week and the year, and what flowed through it. Per network, under its `/app` (`crates/server/src/statistics.rs`), from the server's history table, never the node ([`STORE.md`](STORE.md#mempool_history)). The public form in the reference's shape is `/api/v1/statistics/:interval` ([`API.md`](API.md#mempool-statistics)); this one keeps our twelve bands, which the public one cannot.

| Route | Answer |
|---|---|
| `GET /app/mempool/history/:interval` | `interval` is `2h`, `24h`, `1w`, `1m`, `3m`, `6m`, `1y`, `2y`, `3y`, `4y` or `all`; anything else is `400` |

```json
{"interval":"2h","from":1794471360,"to":1794478503,"step":60,"first":1794477420,
 "minutes":119,"sampled":18,"complete":false,
 "points":[…,
  {"time":1794478500,"samples":1,"count":77664,"vsize":35034159,"fees":12561492,"min_fee_rate":100,
   "bands":[31473971,42955,44248,93275,1645692,162368,510336,793829,206603,60882],
   "in_count":111,"in_vsize":32392,"out_count":7,"out_vsize":2054,"mined_count":0,"mined_vsize":0}]}
```

A mainnet server 18 minutes after its first sample (keys are sent in another order).

- `points` are oldest first, one per `step` seconds (60 for `2h` and `24h`, 600 for `1w`, 3,600 for `1m`, up to whole days for `all`; never more than 1,460). `time` is the step's start, Unix seconds. **A step the server did not sample has no point**: draw a gap where consecutive `time`s differ by more than `step`, never a line across it and never a zero.
- Every value is the **mean over the minutes sampled in the point**, and `samples` says how many (at most `step / 60`). A point with fewer samples than that is partly covered; it is still a fair mean of what was seen.
- `count`, `vsize` (sigop-adjusted vB) and `fees` (sats) are the whole mempool. `bands` is the virtual size in each of the twelve fee bands of [`DESIGN.md`](DESIGN.md#fee-scale), cheapest first, by effective rate: stack them, colored with the fee scale, and they sum to `vsize`. A point recorded before the lowest band was split has ten, all under 0.2 sat/vB in the first: `seriesOf` keeps that as its own layer, drawn until the three finer ones begin. `min_fee_rate` is the node's minimum, sat per 1,000 vB like every rate the WebSocket sends (`100` is 0.1 sat/vB).
- The flow is per minute: `in_count` and `in_vsize` entered the mempool, `out_count` and `out_vsize` left it for any reason, and `mined_count` and `mined_vsize` are the part of what left that a block confirmed. Arrival in vB/s is `in_vsize / 60`. Over a minute, `vsize` moves by about what entered less what left (the totals come from the projected blocks, a moment behind the flow).
- **Coverage.** `first` is the oldest time stored (`null` with none): history begins when the server first ran with its mempool engine on. `from` and `to` are the period answered; `minutes` is how many whole minutes it owes and `sampled` how many it has; `complete` is `true` only when none is missing. The same is in `X-Data-From-Time` and `X-Data-Complete`. Say "since …" when `first` is after `from`, and show holes as holes.
- A new sample lands each minute, about a second after the minute turns; polling a chart every minute is plenty. The first minute after the server starts is never stored (its flow was not watched whole), so the first point appears 60 to 120 s after a start. `Cache-Control: public, max-age=1`. `503` with `Retry-After: 1` when the server has no data directory (`mempool history needs a data directory on this server`; no retry helps) or its store is busy; an empty `points` with `first: null` when it has stored nothing yet.

**The home page** draws what arrived over the last two hours (`2h`, `in_vsize / 60`) beside the next block's map, asked again a few seconds after each minute turns, from the first record when recording began inside the period (`pages/home/incoming.ts`).

**In the frontend** (`pages/mempool/`): `history.ts` has the type, `isHistory`, the intervals, the coverage and flow sentences, `seriesOf`, which turns an answer into the plot's arrays, and what the plot reads from them: the four figures (`figures`), the flow in ten-minute means (`flowPoints`), the band the filter offers (`filterFrom`), the layers from a band up (`layersFrom`) and what the one crosshair reads in both strips (`crosshair`); the page and its tests are beside it. The page draws its own SVG with `components/chart/`'s pure `geometry.ts` and `scale.ts`, not `Chart`: size and flow share one time axis and one crosshair, and its key is the readout and the filter ([`DESIGN.md`](DESIGN.md#mempool-history-not-in-the-prototype)).

- **The page is `/mempool`**, the interval in `?interval=` (24 hours by default), so a link reproduces the view. The header's Mempool section and the home page's mempool panel link to it. Under its panel, "How these figures are made" and "Show the figures" (every stored point as a table, drawn only once opened), then the recent replacements panel ([below](#replacements)), the way to `/rbf`. With no interval in the address, a view whose records begin inside it starts where they do (`fit`), says "Recorded since …", and the picker marks a "Recorded" choice as current; a chosen interval keeps its whole width and hatches the time before the records.
- **One plot.** The size, stacked by fee band in the fee colors, its top the total; under it, on the same time axis, the flow in vB a second: what arrived as a line over what blocks mined and what left otherwise as shades, each point holding its ten minutes' mean where steps are a minute (`flowPoints`, never across a break in recording). The four figures above it say what waits, how that changed, the period's flow weighted by the minutes behind each point, and how deep the next block reaches. The key beside it reads every band and the flow at the crosshair; the readout above the key gives the time, total, count and the node's minimum rate, all of which `aria-valuetext` reads too; the figures table adds, for steps over a minute, the minutes behind each point.
- **Gaps** are `BRIDGE_STEPS`, five steps: up to five missing minutes are drawn across, a longer pause breaks the line into two runs. A lone minute is a sliver, not nothing. Before the step that holds `first` (its point is drawn at the step's start), the plot hatches the period, and a sentence says since when and how many of the period's minutes it holds; when recording began before the period, it says the gaps are times the server was not recording. `all` begins at the day holding `first` and owes only the minutes since it, so it always says since when, even when `complete`.
- **The live edge** is a refetch 3 s after each minute turns, not the `mempool` topic: the newest point is then exactly what the server stored, a mean of the minute, with no second model of it to keep in step. The last answer stays on screen, dimmed, while the next loads.
- **States:** loading; `503` without a data directory, said as such and not retried; nothing stored yet (the first minute appears by itself); nothing in this period, with the time records begin and a link to all of them.
- **Cost,** measured in Chromium at 4× CPU throttling on an Apple M4, with 1,415 points: 36 to 52 ms to redraw the plot on a width change, and the readout and key hold 60 fps while the pointer sweeps it. (The page, from navigation to the drawn plot, took 247 ms.)

#### Replacements

`/rbf` and the recent replacements panel (beside the home page's latest transactions, and the foot of `/mempool`) read the public `/api/v1/replacements` and `/api/v1/fullrbf/replacements` ([`API.md`](API.md#replacement-trees)); `pages/mempool/` holds the page (`RbfPage.tsx`), the panel (`RecentReplacements.tsx`) and the mined status they share (`Status.tsx`), and `lib/replacements.ts` the rest. The home page loads the panel's code lazily: it is the last panel on a phone and the lowest on a desktop, and its list waits for the topic anyway, so a cold home page stays at ten files.

- **A tree is read as a story** (`storyOf`): its line of versions, oldest first, following from the newest back the replaced transaction whose own history runs deepest (the earliest on a tie), so a chain of bumps is one line; everything else the tree removed (children that left with a replaced parent, other conflicts) is listed as also replaced. Each version carries how long it stood (the tree's `interval`). `rise` is the newest rate less the oldest. `mined` is `mined`, `waiting` (the field absent) or `unknown` (`null`: a reorg took its block away). `readTree` drops a list entry it cannot read; it reads trees as deep as the server sends them (at most 100 transactions).
- **Live** (`createReplacements`): the page subscribes to the `replacements` topic ([`WS.md`](WS.md#replacements)) and asks for the list when the version changes, from the server, never the browser's cache ([Following live data](#following-live-data)), and no sooner than `gapMs` after that list was last asked for or answered by any feed on the page (1.5 s on `/rbf`, 10 s for the panel, a glance), so a burst of replacements costs one ask; the topic's next version after `off` (a restart with the engine on) clears the switched-off state; with no topic message after 3 s, or while the socket is down (every 30 s), it asks anyway. The last answer to each list is kept for the life of the tab, so a feed opened again (back to the home page, on to the mempool page) shows it at once and asks for a newer one within the gap: a socket already subscribed sends the topic's first message only once. A story that did not change keeps its object, so its row keeps its element; a new one flashes once. On `/rbf`, a reader scrolled into the list keeps their place: the first story in sight stays at the same height on screen as stories come in above it (the browser's own scroll anchoring is off there, so it is not done twice); with the list's top in sight, new stories come in at the top.
- **States:** the table's rows held while loading; nothing yet; the server's refusal with Try again; the engine switched off (the topic says `off`, or the route `503 the mempool engine is off`, which is not retried).

#### Fee track record

How this server's own fee recommendations, the unrounded numbers behind the home page's "Fee to pay now" (which shows each rounded up), fared against the blocks that followed them, from `GET /app/fees/score?window=…` ([`API.md`](API.md#the-score-kept); what is scored and how, [`MEMPOOL.md`](MEMPOOL.md#the-score-the-server-keeps)). Linked from the home page's "Fee to pay now" ("Track record") and the palette's page list. `pages/fees/score.ts` reads the answer and turns it into what the page says; `FeeScorePage.tsx` draws it.

- **The levels** are named and ordered as the home panel names them (`PRIORITIES` in `pages/home/fees.ts`, held equal by a test, slowest first), each with its share met, its 95% interval and where it stands against its target. The route does not send the target: every level is held to 85% (`TARGET`, from [`MEMPOOL.md`](MEMPOOL.md#against-the-blocks-that-followed), "Against the targets"). A share under it is "Below target" whatever its interval; a sentence beside it says whether the whole interval is on that side. A share or bound under the target never prints as it: a figure that would round up to 85.0% prints as 84.9% (`percent`).
- **The window** is in the address, as the mempool page keeps its interval: `?window=24h|1w|1m|all`, a week without it (long enough for the day-long level to be judged), anything else read as the week.
- **No share without evidence.** A level the route marks `enough: false` shows no percentage, says how many blocks are needed and how many it has, and, when most of its answers are still waiting, that they are. A figure the route sends when `enough` is false is dropped, never shown.
- **States.** A `503` saying the mempool engine is off is not retried (`isBusy` already exempts it) and says the server keeps no record; `503 not ready yet` is retried as every busy answer is, then says the record is not ready with "Try again"; a window with no sample says nothing was recorded then and links to everything; an answer that does not read as the route's, or answers another window than the one asked, is an error, never drawn. A test network says beside the figures that a block with room reads as a miss for an answer at the minimum.
- **Fresh.** The server rebuilds the answer after every 30 s sample; the page asks again each minute while it is visible.
- **Its link preview** is the server's head for `/fees/score` on every network (`crates/server/src/pages.rs`): "Fee track record", and a line saying how often this server's recommended fees on the network were mined in time, against the 85% target. The window in the query is not part of it. `preview.e2e.ts` holds the title equal to the page's.

#### Lightning pages

It holds 30 rows of each kind and shows 30 (`KEEP`), a burst's "and N more" line within them; a kind picker (All, Opens, Closes, Fee changes) keeps the rare opens and closes a press away when fee changes flood the list. It is paused by its button, while the mouse or keyboard focus is in it, and from the start under reduced motion; arrivals then wait, counted in its status, and land as one batch on resume. A row's time is the only text that ticks, and rows keep their elements as batches arrive, so a focused link survives both. The list has no live region. Anything after the first answer counts, from the socket or over HTTP. With no snapshot 3 s after the page opened (an empty feed sends none), or while the socket is down (every 30 s), it asks `/feed` instead. Its box holds one height, so its arrival moves nothing: beside the movers it fills their height (at least `18rem`) and scrolls inside, and below 65em it is `min(26rem, 65svh)`. **Movers** are one request a period; the four lists, and the largest either way merged from them, are a press away. The chart below keeps hatching the time before the record across its period. **The chart** draws the pressed figure as a line over its whole period, the time before the first record hatched, a median's mean in the readout; the series is samples (`marks`). `LightningNav` (Overview, Rankings, History) heads every Lightning page; the overview, the rankings and the search remember themselves (`rememberList`) so a node or channel leads back to the list the reader came from; "History" lands on the chart once the sections above it have answered.

When every peer is listed, what those do not add up to was on channels whose two ends are the node (counted in its figures, listed with no peer), said by kind; with no peer at all, every one was. When some peers are left out, the two cannot be told apart, so it gives the record's totals and the listed peers' apart and attributes nothing more. A peer's share is of its force closes and penalties together, worked out from its counts. A node that left the graph is headed with its key and a line saying it has no open channel now and that below is what this server holds, when it has a close: its record and its closed list (`ClosedList`, its node made from the record's counts), whose route answers from the store for such a key ([`API.md`](API.md#a-nodes-channels)); its peers filter that list as a held node's do. A key with no close is "This server knows no such node"; a record that fails any other way says it could not load, with Try again, never that there is no such node. The glance's "Closes seen" gives counts by kind and no share of its own.
- **A channel** is one request (`/app/lightning/channels/:id`). What it draws and the node page can reuse is shared: in `lightning.ts`, `msatAsSats` (a policy's msat as sats, exact to the msat at any size; a bigint past 2⁵³) and `msatAsBtc` (in magnitude from a sat, for an overview's narrowest rooms only), `parseSats`, `hopFee` (base fee plus the proportional part in bigints, that part rounded down to the msat as nodes do) and `htlcLimit`, `TERMS` (each policy term's label, figure and how two ends differ), `channelTag` (a channel's state in words, a missing policy apart from a disabled one), `lifeSteps`, `closeShown` and `shortName`; in `parts.tsx`, `Icon`, `Tag` and `KindTag` (a state or a close's kind as an icon in its tone and a word), `ChannelId` (wraps only after an "x"), `Fig` and `MsatFig` (a figure whole with its unit; one longer than 12 characters carries its magnitude, shown in its place only below 15em, a phone at a large text size) and `NodeName`, the name with the key beside it. `continued_as` and `continued_from` are read as none when a server older than them leaves them out. A closed channel's words come from `closeWords`, which gives a penalty's once a revocation sweep is recorded whatever kind the closing transaction shows, on the channel page and the transaction page alike.
- **Fee history** (`ChannelFees.tsx`, and "Recent fee changes" in `NodeCharts.tsx`; [`API.md`](API.md#fee-history)). An open channel with a policy asks `/channels/:id/fees` after its own answer, the section holding its height meanwhile; a closed one asks nothing. Each way is a panel in its lane's colour, titled with who charges whom and the current rate: with two records or more a chart of the rate, loaded only then, whose points `feeSteps` makes from the records and `watched` (a step holds each rate until the next, a `null` in each gap, the last stretch run on to when the answer came, so the clock redraws nothing); with one, since when no change was seen; with none, that nothing is recorded. "Show the figures" lists the records, newest first, with base and inbound fee columns only when a record has one (`Chart`'s `table`); at 200% text it is a labelled list, as the node page's tables are. The readout writes a rate past 10 000 000 ppm in magnitude. The life of the channel counts the changes held (`changesIn`: an end's first record is where watching began) and links to `#fee-history`, which a link from elsewhere scrolls to. The node's Fees view asks `/nodes/:key/fees` only when open: ten rows, each the channel (the row opens its fee history), the peer as text, whose fee moved, from and to, and when; where the rate held, the row shows and names the fee that moved (`changeShown`), so none reads "from 500 to 500".
- **Inbound fees** are lnd's ([`LIGHTNING.md`](LIGHTNING.md#inbound-fees)), shown only when not zero both ways (`inboundOf`) and named by sign (`inboundWord`): negative a discount, positive a surcharge, mixed an inbound fee; each figure signed (`InboundFig`). On the channel page, a note in its end's lane and two terms in "Policies side by side" (absent as zero for the difference); on a node's rows, a small line under the fee it belongs to; on a card, under the chevron, so a card keeps its three lines. The hop's fee leaves it out, and says so in its disclosure.
- **Search** is the header's field: Lightning has no box of its own. A compressed public key (66 hex digits, `02` or `03` first) opens its node page (an uncompressed one, 130 digits from `04`, is never a node's and opens its address page; a compressed one does only from a link to an address page or a `bitcoin:` URI) and a channel id (`811984x2037x0`, or the 64-bit number it packs into, when that is too big for a height) its channel page, with no request, on any network; the page says when Lightning is off. Other text of 3 to 66 characters, on a network `/app/config` lists under `lightning` (a network without Lightning is never asked to search), is a node name or a key's start: once typing pauses for 280 ms the field asks `/app/lightning/search` and lists the nodes it returns under the field as a WAI-ARIA combobox (arrows, Enter, Escape, a press), each with its name as text (`cleanAlias`), its key shortened beside it and its capacity, then a last row, All results for “…”. Each edit aborts the request in flight and a slow answer never replaces a newer one, so one reader typing costs at most about 3.5 requests a second, under the per-client limit ([`CONFIG.md`](CONFIG.md)). Enter with no row picked opens `/lightning/search?q=`, whose heading repeats the query; on a network without Lightning the text reads Not recognised as before. A name matches many nodes, so the results page is a list, and links and bookmarks to it keep working. The channel the server's search can also return never shows in the list: every channel id it parses reaches the channel page first.
- **The penalties** (`PenaltiesPage.tsx`) are one request a page (`/app/lightning/penalties`), the page in the address from 1 (`readPage`; anything unreadable is the first), the old rows held and marked busy until the next arrive. A table on a wide screen, cards on a phone; with none, one line saying since when the server has watched (the answer's `from`), no table. The overview's closes by kind link to it beside their 30-day sum.
- **The transaction page's note** (`TxLightning.tsx`, the one import the transaction page takes from here) asks for a confirmed transaction only: the status, then `/app/lightning/tx/:txid` when it is `synced`. A network whose status said `off` is not asked again in that tab. The part that draws the note (`TxChannels.tsx`) is a lazy chunk loaded only when the answer lists a channel, and it sits after everything else on the page, so its arrival moves nothing.
- **The block page's panel** (`BlockLightning.tsx`, the one import the block page takes from here) sits directly under the block's facts, above the map and the transactions. It asks `/app/lightning/block/:hash` together with the block's own requests, only on a network `/app/config` lists under `lightning`: one request, about 0.5 KB, on a block of such a network, none elsewhere. A page opened by height asks once the height has given the hash, with the rest of the block's requests. `BlockLightning.tsx` checks the answer and draws the closed `<details>` and its summary itself, so the panel appears with the answer, without waiting for more code; the list inside (`BlockChannels.tsx`, a table on a wide screen and cards on a phone, `usePhone` as the node page) is a lazy chunk loaded only when the block has channels, with the Lightning chunks it shares. No space is held for it, since most blocks have no channel. Measured on mainnet blocks with Chromium (three cold loads each, 2026-11-16): on a phone (390 px) the panel adds no layout shift (0 unthrottled, 0.0003 on Fast 4G, the same as a block without channels), as what it moves is below the fold; at 1280 px it moves the facts panel below it once, 0.009, for a total of 0.011 against 0.002 on a block without channels, unthrottled and on Fast 4G alike. A refusal, a graph still syncing (a `503` the browser logs, which `withRetry` asks again for up to a minute, so the panel appears if the graph syncs meanwhile), an unreadable reply or a block with no channel shows nothing at all; a test that lists Lightning in `/app/config` on a server without it must answer this route.
- **Names are attacker-controlled text** ([`SECURITY.md`](SECURITY.md) rule 14). `cleanAlias` turns control characters and invisible format characters (bidi overrides and isolates, zero-width spaces; not the joiner emoji are built with) into U+FFFD, so a reader sees something is there, and thins stacked combining marks to two. `Alias` isolates the name in `<bdi>`, cuts it to 32 characters in lists (64 as a node page's title, with "Show the whole name"), counted as a reader counts them (`Intl.Segmenter`), and puts at most 512 in its `title`. The public key is always beside the name, and the node page says the key is the identity. Addresses are text chips, never links.
- **A node's colour is shown once,** in its Identity section: a swatch beside the `#rrggbb` it announced (anything else shows as none), set through the `style` object as a custom property, which the Content-Security-Policy allows. Nothing else on the site takes a node's colour.

#### Arkade VTXO

`pages/ark/arkade/` reads `GET /app/ark/arkade/vtxo/:txid/:vout` (`crates/server/src/ark_arkade.rs`). The answer is what the network's Arkade server says, with one field of ours: `vtxo` (amount, script, times, `preconfirmed`, `swept`, `unrolled`, `spent`, the txids it names), `server` (`signer_pubkey`, `exit_delay_secs`), `chain` (the transactions that take it on chain, as arkd lists them, each `txid`, `kind` `commitment`, `tree`, `checkpoint`, `ark` or `other`, and `spends`), `chain_complete` (false when the chain passed 128 and was cut), `batches` (at most two, each with its tree root first, or `null` when it is larger than 512 nodes), `batches_omitted`, and `onchain`, per chain transaction where our node has it (`off`, `mempool`, `confirmed` with `height`, or `null` when the node did not say). `404` is `vtxo not found` or, on a network without `{NET}_ARKADE_URL`, `arkade is not available here`; `502` and `504` are the Arkade server failing.

- **Read strictly** (`readAnswer` in `vtxo.ts`): txids 64 hex digits, counts safe integers, the server's caps held, `onchain` as long as `chain`; anything else is "could not be read". Nothing in it is ever markup.
- **The exit** (`exitSteps`): commitments first, then each transaction after what it spends; a tree transaction is a Leaf when it ends a branch, a Branch otherwise; `ark` reads Transfer. The page names them in its words, Arkade's beside them in muted text.
- **The picture** (`layout.ts`, drawn by `Tree.tsx` in SVG): the batch trees in quiet ink grown up from their commitments on the Bitcoin line, which runs from the commitment through now to the expiry, this VTXO's branches in the accent, its checkpoints and transfers above the leaves. Without a tree, only the chain's own branch, and the batch's VTXOs as a count. Laid out again on a resize and each minute, never each second. "Play exit" lights the steps at `--dur-slow` each and ends on the wait after an exit; under reduced motion it shows the end at once. The transaction table is its text alternative.
- **Kept current**: asked again on each new block or reorg, and every 30 s while in view (`POLL_MS`); the server keeps the Arkade answer 30 s, so a block mostly costs a node lookup.
- **Reached from the Ark entry page** through `/ark/vtxo/…`, which opens it when Arkade alone knows the outpoint (`pages/ark/lookup.ts`, [`ARK.md`](ARK.md#the-entry-page)).

#### Arkade address

`pages/ark/arkade/AddressPage.tsx` reads `GET /app/ark/arkade/address/:address?page=n` ([`ARK.md`](ARK.md#an-addresss-vtxos)): `page`, `pages` and up to 25 `vtxos`, read strictly (`readListing` in `address.ts`). The page in the address is `?page=n` (`paths.arkadeAddress(address, n)`); a page's answer is held while the next loads. The shape decides, before any request, what the page can say alone: not an Arkade address, a Bark address, an unknown version, another network's (`addressKind`, by BOAT-1); the server's checksum and key checks follow. The figures count only the page shown ("on this page" when there are more): no total over pages is ever computed. Spendable is arkd's word for neither spent nor swept. Asked once, not polled.

#### Decoder

`pages/decode/DecodePage.tsx` sends the fragment's string to `POST /app/decode` ([`API.md`](API.md#decoding)) and reads the answer strictly (`isDecoded` in `decode.ts`). A node or channel is a link to its page on the network the answer's `names` gives, only when that graph knows it; otherwise its key or id is text with a copy button. A decoded URL is text, never a link, its host set apart. Only the expiry's words follow the clock.

**A raw transaction** (whatever `readPasted` in `pages/push/push.ts` reads as hex) is not sent to `/app/decode`: it goes to `POST /app/tx/check` ([`API.md`](API.md#checking-a-transaction)) on the first network in `/app/config` (mainnet when the server has it), the network named beside the heading. It is drawn by `CheckedTx` (`pages/push/CheckedTx.tsx`), the broadcast page's own result, without the button; its links stay on that network (`NetworkScope` in `lib/page.ts` sets the network `useNetwork` and `createApi` read). When the server broadcasts and the node does not have it, a "Broadcast" link opens that network's broadcast page with the hex in the history entry's state, never in its URL; that page reads it as if pasted.

**The service an LNURL or Lightning address names** is asked from the browser, once, as soon as the result shows (`service.ts`, allowed by `connect-src 'self' https:`, [`SECURITY.md`](SECURITY.md) rule 15): a pay, withdraw, channel or untagged LNURL, or a Lightning address; never a login link. One `GET` of the decoded URL, only over HTTPS to a public name (no address literal, no `.local`, `.home.arpa`, `.onion` and the like: those read "Not asked"), with no cookies and no referrer, no redirect followed, 8 s to answer whole, at most 64 KB read; it is aborted when the box is edited away from the decoded string, or the page is left. A login link is known by its tag as the service reads it (percent-decoded, any case), and every `keyauth://` link is one. The callback, the second step that would ask for an invoice or a withdrawal, is never called. Every field is read strictly and shown as text: the kind, the least and most in sats, the `text/plain` description (or `defaultDescription`), the long description and identifier, the comment length, the callback's host (with "Other host" when it is not the one asked), a channel request's node; images, HTML and links in the answer are not shown. A service's `{"status":"ERROR"}` shows its reason. Failures are one line each: asking, no answer in time, "Could not ask <host>" (a refusal to answer another site's page and a network fault look the same to the page). The footer links here from every network's pages. Search sends a payment string here by its form alone (`payment` in `search/query.ts`: a prefix, or for a Lightning address an email's shape with a dotted domain), from any network, and its field takes 8,192 characters for them; everything else it reads is still capped at 512.

#### Broadcast

`pages/push/PushPage.tsx` reads a signed transaction pasted as hex and sends it only when the reader presses the button. The hex stays in the page: in no URL, in a `POST` body each time. The result (`CheckedTx.tsx`) is shared with the [decoder](#decoder), which can hand a transaction over in the history entry's state.

- **Read as soon as it is pasted** (`readPasted` in `push.ts`): whitespace anywhere is dropped, so wrapped hex works; not hex, an odd number of digits or more than 800,000 digits is said under the box with nothing asked. A paste is read at once, typing after a 400 ms pause. Then `POST /app/tx/check` ([`API.md`](API.md#checking-a-transaction)), read strictly (`readChecked`); the last answer is never shown beside a box that holds another transaction.
- **Shown with the transaction page's parts**: the summary (fee, amount, size), the flow and the inspector from `pages/tx`, fed the check's Esplora-shaped `tx` with no spends.
- **Warnings** (`warnings`): a fee rate above ten times the next block's (`/api/v1/fees/recommended`), never below 100 sat/vB, and 1,000 sat/vB when the next block's rate is not known; sats in `OP_RETURN` outputs; inputs whose output the node does not have. The first two make the button "Broadcast anyway", unfilled; the third only warns, as the node's refusal will say it too.
- **Known to the node**: "Already in the mempool" or "Already confirmed", a link to its page, and no button.
- **Sending** (`broadcast`): one `POST /api/tx`, never retried by itself. "Sent" links to the transaction's page, which follows it live; a refusal is one line (`refusal`): the node's reason, the seconds to wait after a `429`, or that the server does not broadcast.
- **When the server does not broadcast** (`broadcast: false` in `/app/config`): the page still reads a transaction and says so, with no button, and the footer has no link to it.

#### Timestamp proofs

`pages/timestamp/TimestampPage.tsx` checks an OpenTimestamps proof (`.ots`) against this server's own node, in the browser. The reader gives the proof and the file, or the file's digest as hex; the page follows the proof from the digest to a block's merkle root and says whether they meet.

- **The reader's file never leaves the page, nor does its digest.** It is hashed here, 4 MiB at a time (`digest.ts`): memory stays at one chunk whatever the file's size, the page draws between chunks, and "Stop" aborts between them. A 200 MB file hashed in 0.8 s in headless Chromium on the dev machine (about 250 MB/s), the browser's memory rising 108 MB at most and no frame longer than 17 ms. `crypto.subtle` has no incremental digest and is missing on a plain-HTTP page (rule 8 above), so the four hashes a proof can name are our own (`hashes.ts`: SHA-256 and SHA-1 from FIPS 180-4, RIPEMD-160 from its authors' paper, Keccak-256 with the original padding), tested against their published vectors. The file is hashed with the proof's own file hash, again if a proof naming another arrives.
- **The only requests a proof causes** are for the blocks its Bitcoin attestations name: `GET /api/block-height/:height`, then `GET /api/block/:hash/header`, on mainnet, each height once (every path to it is compared with that one header), one block at a time, lowest first, at most 8 distinct blocks a proof. The height's answer must be a block hash before a header is asked by it. None is made before the digest matches the proof's, or for a proof with no Bitcoin attestation. `timestamp.e2e.ts` checks every request a test's page makes.
- **The network.** Bitcoin attestations are mainnet's. The page is mounted on every network (`/signet/timestamp` too) and always asks the root's `/api`, the mainnet one, when `/app/config` lists mainnet; it says so on a test network's page. Without mainnet it asks nothing and says the server cannot check the block.
- **The byte order.** The proof commits to the merkle root as the header stores it, the reverse of the API's `merkle_root` text. The page compares the path's last value with bytes 36 to 68 of the 80-byte header, after checking that the header's double SHA-256 is the hash the node gave for the height; the `merkle_root` text is never read. The steps' end shows both orders.
- **The proof is hostile input** (`ots.ts`). Read with a stack of our own, never by recursion, and bounded: 256 KiB a file, 1,000 operations from the digest to any attestation, 10,000 operations and 256 attestations in all, 4,096 bytes an argument or a message (the format's own limit), 8,192 an attestation's payload, 1,000 a calendar's address, an append or prepend of at least one byte, 4 MiB hashed in all (under the other bounds a proof can ask for about 6 MiB, so this is the bound that refuses; a real proof hashes a few kilobytes); a length is checked against what is left before it is read. Anything wrong is a `ProofError` of a kind the page names: not a proof, cut short, a version or an operation it does not read, too large, or damaged. `fuzz.test.ts` runs 5,000 random and mutated proofs in the suite (cut, bits flipped, huge lengths, deep runs, repeats), held to how each one ends, and 50,000 in its long form, which also holds each input to its processor time with `cost()` and so runs on request, as a time budget must (`FUZZ_LONG=1 bunx vitest run src/pages/timestamp/fuzz.test.ts`), and the work bound exactly: a proof of nine branches that hashes 4,194,304 bytes, the bound itself, is read, and one hash more is refused, `walk` counting only hashes it finished. Keccak-256 is the slowest of the four: that proof in Keccak-256 took 285 to 430 ms of processor time on the dev machine (seven runs in Bun, median 297 ms), in SHA-256 224 to 264 ms.
- **The format, as read:** the 31-byte magic, version 1, the file's hash (SHA-256, SHA-1, RIPEMD-160 or Keccak-256) and digest, then the tree: each item an attestation (a zero byte, an 8-byte tag, a length-prefixed payload) or an operation and the tree that follows it, with `0xff` before every item but a node's last. Operations: append and prepend (with an argument), SHA-256, SHA-1, RIPEMD-160, Keccak-256, reverse, and hex (lower case). Attestations: Bitcoin and Litecoin (a height), pending (a calendar's address), and any other tag, whose payload is skipped and which is named, never checked. An unknown operation cannot be skipped, so it is "an operation this page does not support", never a verdict.
- **Verdicts** (`verify.ts`): verified by the earliest Bitcoin block whose root the path reaches, the others listed as also verified, not reaching their root, unknown here, could not be checked (a request that failed, which never undoes a verified one; only when every request failed is the whole check an error to try again), or not checked (past 8 blocks); not for this file, or, for a pasted digest, not the digest the proof starts from; does not verify, only when every Bitcoin attestation was checked and none reached its root; not fully checked, when none verified and some were past the cap, failed or name a block this node does not have, which lists each and calls nothing damaged; a block this node does not have (every height a 404); pending, with the calendars as text and how to upgrade; no Bitcoin attestation; no mainnet here. Litecoin, calendars and other notaries are "not checked", never failed. A proof or a file the browser cannot read is said to be unreadable, never judged by its format. A replacement proof or file takes the last verdict down at once ("Reading the proof", or the hashing's progress), a file is hashed again only when it or the hash it needs changes, and a verdict is shown only for the proof, digest and source it was reached for.
- **What a verified proof says depends on what the reader gave.** A file the page hashed: "This file existed before block N". A digest typed or pasted: "This digest is committed to by block N", and that whatever has that digest existed before then, the page having seen no file. The block's time is called its header time, the miner's claim, with the two checks a node makes of it (later than the median of the blocks before it, up to eleven; no more than two hours ahead of the node's own clock when it checks; the genesis block's header is fixed by the network's rules and its time is checked against nothing: `headerTimeRule`) and nothing inferred about when the block was mined. A file named by its SHA-1 gets a line that different files can share one; SHA-1 used only inside the path gets a line on what a collision there allows (two different values giving the same next value), and that the file's own digest is not SHA-1.
- **Each choice owns its result.** A proof's read and a file's hash count only for the choice that started them: a later choice or a removal makes an earlier read moot, and a replaced hash ends unseen; only the reader's Stop shows "Hashing stopped".
- **Shown as text:** everything from the proof. A calendar's address is never a link. The path's steps sit behind a disclosure. Only on a path that verified, a step with the form of a transaction id is named as such (a link to its page on mainnet) and the climb to the block's merkle root has each level as one step; a path that did not verify is listed as computed, naming nothing.
- **Not built: upgrading a pending proof** from its calendar. It would be one `GET` to the calendar's address (allowed by `connect-src https:`), but it sends the proof's commitment to a server the proof's maker chose, and tells it that this visitor holds that proof now. Left to the owner.
- **Fixtures:** `fixtures/ots` (its README says where each came from); `timestamp.e2e.ts` serves mainnet's recorded headers in place of regtest's.

### Live data

`lib/live.ts` holds one WebSocket per tab and network to `/app/ws` ([`WS.md`](WS.md)). It opens while any component is subscribed to a topic and closes when none is. It checks the greeting's protocol version and network, subscribes after it, reconnects with exponential backoff and jitter (0.5 to 30 s), resubscribes, pings every 30 s to find a dead socket, sends subscription changes at most every 250 ms (unsubscribes before it subscribes, so switching between capped topics never holds one too many), and ignores message types it does not know. Binary frames are read as `ArrayBuffer`s and offered to every subscribed topic that has a `binary` reader; the others never see them. A hidden tab keeps its socket; a socket that drops while hidden, or while the browser is offline, waits until the tab is visible and online again. After close codes 1002–4002 or a greeting from another protocol version it stops for good: the page is out of date.

A topic is a name and a parser, and a binary reader if it sends binary frames. Write one per topic in `lib/`, as `blocks-topic.ts` does; the client never changes for a new topic:

```ts
export const mempoolTopic: Topic<MempoolMessage> = {
  name: "mempool",
  // Return undefined for a type or shape this page does not know: it is ignored.
  parse: (m) => (m.type === "delta" && isDelta(m.delta) ? { type: "delta", delta: m.delta } : undefined),
};
```

A component uses it for as long as it is mounted, on the page's network:

```ts
useTopic(blocksTopic, {
  message: (m) => { /* every message, in order; the first is the topic's current state */ },
  resync: () => { /* the socket reconnected and messages may be lost: refetch over HTTP */ },
});
const status = useLiveStatus(); // "connecting" | "live" | "reconnecting" | "offline"
```

- **Load over HTTP, then keep up over the socket.** The socket only reports changes. Fetch the state with `fetchApi`, apply messages on top, and treat a gap, a `resync` message that disagrees and the `resync` handler the same way: fetch again. Messages that arrive while that fetch is in flight are held and replayed on its answer (`pages/home/feeds.ts`, `createBlockFeed`).
- **The mempool topics** exist now ([`WS.md`](WS.md#mempool-topics)): `mempool` for the mempool panel and bar, `projected` for the projected tiles, `transactions` for the latest transactions, and `projected-txs:N` for one projected block's grid. The first three are JSON and each message is the whole state, so a page keeps the last one; `projectedTopic` in `lib/projected-topic.ts` reads `projected`, with rates turned into sat/vB. `lib/mempool-topics.ts` reads `mempool` and `transactions` the same way. On a server with the mempool switched off each topic sends `{"type":"off"}` once. Rates on the wire are in sat per 1,000 vB.
- **A projected block's transactions** (`lib/projected-txs.ts`). `projectedTxsTopic(n)` reads block `n`'s frames with `decodeFrame`, which never throws: a frame of another kind is ignored, one in a newer format version comes back as `version` (ask for a reload), and one that is cut short, too long, has nonzero padding or a fee beyond 2^53 comes back as `malformed`. `BlockTxs` keeps the block as a `Map` from txid to a `GridTx`-shaped record (`{ id, vsize, fee, rate, flags }`, rate in sat/vB, flags read by `readFlags`), the same object until its record changes (its flags included: a child arriving sets "paid for by a child" on a transaction already there). `apply(frame)` answers `changed` (with the txids that came in and went out), `lost`, `ignored` or `version`. On `lost`, call the function `useTopic` returns: it unsubscribes and subscribes again in the next batch (`LiveConnection.restart`), and the snapshot that follows starts the block over. Until it comes the model keeps the last picture and ignores the old subscription's deltas still in flight, so one gap never becomes a loop. Call `expectSnapshot()` from the topic's `resync` handler: a reconnect subscribes afresh. A page holds at most two of these topics at once, and leaving the page unsubscribes. `fakes.ts` builds frames for tests (`snapshotFrame`, `deltaFrame`, `fakeTxid`).
- **A new block and the mempool topics arrive in a promised order** ([`WS.md`](WS.md#when-a-block-is-found)). For a new block, the `block` message comes first, then the mempool topics already on that block, sent at once rather than at the 2 s rate. No mempool message on an older tip follows the `block` message. The next `projected` after a `block` is on that block within milliseconds on regtest and about 0.6 s on mainnet, and the server sends an older one after a block's message only if its engine is still behind 3 s later; that message's `tip` says so. A transaction leaves the projection at the same moment, and a followed transaction's `tx:` topic says `confirmed` at the same moment, not at the next interval. `fees` on our own projection keeps the same order. So the home page draws a block as it is announced, crossing from the projection on its parent, and takes the next projection as the state after it; it holds back a projection on a block it has not shown (`HOLD_MS`, 3 s, `pages/home/projection.ts`) only while the strip catches up over HTTP after a gap or a reconnect, where the order does not reach: one `/blocks` request and, behind the server's one-second tip cache, one retry (`STALE_RETRY_MS`, 1.2 s, `pages/home/feeds.ts`). A new tile's facts are asked for over HTTP only when its `summary` has not come `PUSH_GRACE_MS` (4 s, `pages/home/summaries.ts`) after the block; on mainnet it came 1.6 to 3.4 s after it, audit included. The projected-block page waits at most `FOUND_WAIT_MS` (`pages/projected/state.ts`) for the block's new picture, which follows the projection at once, before saying the block was found.
- **The home page's fees** (`pages/home/fees.ts`) come from the `fees` topic alone while the socket is live: the levels the server gives, printed rounded up at a fee rate's usual precision (`formatFeeRateUp`), neighbouring levels that print the same rate shown as one answer (`groupLevels`), the node's fallback (`source: "node"`) said so beside them, and `unavailable` shown as no number. While the socket is down, or when the topic has said nothing 5 s after the page opened, the page asks `/v1/fees/precise` at once and every 30 s instead, keeping the topic's last answer until a reply replaces it (an HTTP answer the next ask cannot confirm within 2 s is taken down); that answer is ours when it carries a chain-tip stamp and the node's when it does not ([`API.md`](API.md#fees)).
- **The home page's mempool** (`pages/home/live-mempool.ts`) takes the panels and the strip from those topics and asks `/api` for nothing they send. It polls `/mempool` and `/mempool/recent` instead only when the server says `off`, while the socket is down, or when the topics have said nothing 5 s after the page opened (a server still making its first mempool cycle). `stale: true` keeps the last state on screen and turns the live indicator to "Node not answering".
- **Following one transaction or address:** `tx:<txid>` says where a transaction is and what happened to it (in the mempool with its projected block, replaced with the whole chain of replacements, confirmed, evicted, or unknown), and `address:<address>` sends a token that changes whenever the address's history does, so the page refetches. Each message is the whole state. The messages, what each state means for the page, how to phrase the position without false precision, and the bounds (four transactions and two addresses per socket) are in [`WS.md`](WS.md#following-a-transaction-or-an-address). On `unknown`, ask `GET /api/tx/:txid/status`: the topic never asks the node. On `refused` with `server_full`, fall back to polling the HTTP status and try the topic again later.
- **`lib/track-topics.ts`** reads both: `txTopic(txid)` gives `TxMessage` (a state with `stale`, or `off`, or `refused`), rates in sat/vB; `addressTopic(address)` gives `watching` with its status, `unavailable` or `refused` with a reason, and names the topic as the server does (bech32 in lower case). `linksOf` reads replacement links, which the topic and `/app/tx/:txid/replacements` share.
- **The transaction page's state** is a pure model in `pages/tx/state.ts`: the topic and the HTTP status route are two witnesses, and the newest word wins. A topic message decides only when it is live, not `stale` and not `unknown`; an HTTP "waiting" never hides the topic's position, since both agree; a 404 keeps what the topic or the replacement record knew about why it left. The page follows its transaction (and `blocks`, for confirmations) only while something can still change, and the newest replacement's topic when it was replaced: at most two `tx:` topics. A young confirmed transaction's first `unknown` asks nothing more; a later one, a first one after an answer that it waits (it left the mempool before the page followed it), or one on a new block, asks the status route. An HTTP answer counts as of when it was asked, so a topic message heard while it was in flight wins. A live socket whose topic has said nothing for 5 s (a server still making its first mempool cycle) counts as not live, and the page checks over HTTP. A transaction the node did not know when the page opened is checked for until it appears.
- **The address page follows first, then asks.** It asks for the totals and the first page of history only once the `address:` topic's first message has come (a few milliseconds when the socket is open), so a payment made before that status is in what it asks for, and one made after it changes the status. With no message within a second (the socket still opening, or a tab opened in the background), or when the first message is `unavailable` or a refusal, it asks anyway, and then takes the first status that comes for a change. Its address requests skip the browser's HTTP cache (`createApi(…, { fresh: true })`): an answer kept for its `max-age=1` second can predate the change the page was told of, and when the history came from the cache while the totals came from the server, the refresh stopped with the totals new and the new row missing (on regtest, 27 of 80 page loads timed to a second's turn, none of 50 once fixed). A refresh that still brings nothing new is asked again after 1, 2 and 4 s, in case the node's index trails its status: on regtest the node's address routes already showed the change when its Electrum notification came, in 210 of 210 payments and blocks. Each of those refreshes also brings the balance chart up to date with one summary page ([below](#the-address-balance-chart)). While a request waits out a busy refusal (429, or a 503 that says to wait), the page says so in one quiet line (`busyRetrying`); one that gives up shows as busy, with Try again, never as an error (`ErrorState` for `isBusy`). A change heard while a fetch is in flight restarts it. A later page that lands after a refresh changed the first page is dropped, since it may continue rows that are gone, and the page asks again after the rows the refresh left, so "Show 25 more" always shows more.
- **An address's history waits for its totals.** The first history page is asked once the totals have answered, or after `HISTORY_WAITS_MS` (1 s) if they have not, and never after a "too large" answer: the node refuses those totals within tens of milliseconds, and a page of such an address's history can keep it busy for a minute or more (95 to 102 s measured on the largest found, [`API.md`](API.md#very-large-addresses)). The history section then says the transactions are not available, as it does when the server refuses the history itself.
- **A public key** in the address's place (`recognise` in `lib/address.ts`: type `p2pk`, on every network) is the page of the outputs paid to that key itself, which have no address ([`API.md`](API.md#public-keys)). The heading says Public key and there is no QR code, since a wallet that scans a key cannot pay it. The node names no address on such an output, so a row's amount is found by the output's script (`keyScript`, in `netChange`), and the lookalike check is not run: the page has no address of its own to imitate. A key that is not a point on the curve gets the server's `400` and the page says it is not a valid public key. On the transaction page a pay-to-pubkey output's card and its inspector show the key (`scriptKey`), linked here.
- **A silent payments address** (BIP352, `sp1…` on mainnet and `tsp1…` on the test networks; `pages/address/SilentPayment.tsx`, `silent-payment.ts`) is read in the browser: no payment names it on chain, so the node has nothing to say about it, and the page makes no API request and no WebSocket subscription for it. (The page's own URL still carries the address, so opening or sharing the page sends it like any page request.) `recognise` takes its form (bech32 characters, up to 1023 in all, at least the 116 of version 0) and leaves the rest to the page, which checks the bech32m checksum, the version (31 is refused; 1 to 30 are read by their first 66 bytes, as BIP352 asks, with a one-line note that a wallet may not pay them), the length its version needs, and that both keys are compressed points on secp256k1. It shows the verdict, the scan and spend keys with copy buttons, and, behind a disclosure, why there is no balance or history. Search also finds one in a `bitcoin:` URI's `sp` parameter (BIP321) when the URI's path holds no address.
- **An address above the node's cap** (`pages/address/Large.tsx`) shows, in place of the totals, chart and history: how many transactions have paid it and the node's cap from `/app/address/:a/size` (checked by `readSize`; without them it says the same in words), its unconfirmed transactions from `/txs/mempool`, then what is not shown and why in two sentences. The node will not watch it, so the list is asked again every `POLL_MS` (10 s, `poll.ts`) while the tab is in view and at once when it comes back; newcomers go on top with the usual flash and rows already shown keep their elements (`arrivals`), so focus survives a refresh. A failed check keeps the last list and says so. It never asks for the address's history, balance history or unspent outputs ([`API.md`](API.md#what-the-page-shows-of-such-an-address)).
- **An address the server adds up and keeps** (`pages/address/Kept.tsx`, `ledger.ts`; [`API.md`](API.md#very-large-addresses)). Once the totals have answered, the page asks `/app/address/:a/ledger` (from the server's memory and store, never the node) and parses it strictly (`readLedger`: anything unexpected reads as nothing known). Its first history page waits for that answer too, so a kept address never asks for a history the server would refuse.
  - **Being added up** (`queued`, `seeding` or `busy`, after totals refused for size or slower than 5 s): the large page above, led by a panel that says it is being added up once and will then be instant, with real progress: its place in line, or the seconds since the server began, counted on by the page between asks. The page asks again every `LEDGER_POLL_MS` (3 s) while it waits and is in view, which also keeps its place (the server drops a seed nobody asks about for 2 minutes). `failed` says so; `refused` (the node's cap is in force) leaves the large page exactly as before the ledger.
  - **Kept** (`tracked`): the totals, which the server now answers from its ledger through the page's usual request; a line saying since which block the server has kept it and which block the totals are exact at; the balance chart from when tracking began (the ledger's points, one a day or so); then its transactions, by where its whole history stands (the ledger's `history`):
    - **`whole`:** every confirmed transaction, from the server's own pages ([`API.md`](API.md#paging-a-kept-history)): the history list of an ordinary address (`History` with `kept`), headed "Transactions" without the unspent outputs view (the server keeps none), its first page from `/txs/chain` and "Show 25 more" from `/txs/chain/:last`, the count out of the confirmed total.
    - **Otherwise** its newest confirmed transactions, at most 200, 25 at a time ("Show 25 more"), with time, amount and block, and one sentence saying why the list stops there: the server is getting the whole history from its node (`none`, `taking`: the page's own ask is what makes it), the node declines to list it (`refused`), the server let it go to make room for addresses viewed more lately and is getting it again, or takes it again when the page is open after a given time (`dropped`, with `history_again`), or it is larger than the server keeps (`too_large`). While `filling`, that sentence (or the empty list) also says the transactions from before the block it began keeping it at are added once the node has listed them.

    And its unconfirmed transactions as on the large page. While the page is open and in view it asks for the ledger again every `KEPT_POLL_MS` (5 minutes, `asksAgain` in `ledger.ts`), one read of the server's store: the server takes (or takes again) a whole history only for an address being viewed, and drops none viewed in the last 30 minutes, so a reader paging a long history keeps it. The topic says `ledger` with the new height when a block changes it, or when a fill or the whole history is done, and the page asks for the ledger and the totals again, and its first history page when the history is whole.
  - The figures wrap: between 40em and 80em at least 12rem a column, on phones two abreast where each has 9.5rem and one below, so an exchange's millions fit at 320 px in wide faces.
- **Say when it is not live.** While `status()` is not `live`, poll what the socket would have sent, no faster than every few seconds, and tell the reader (the home page's indicator).
- In tests, stub the global `WebSocket` with `FakeSocket` from `lib/fakes.ts` and play the server: `FakeSocket.last().hello()`, `.receive({...})`, `.drop(1006)`.
- **The block page follows the newest block.** From its first ask until its status names a next block, the page hears `blocks`. Once the status says nothing comes after it, a tip that is another block, heard before that answer or after, a reorg or a resync asks the status again, from the server, and the next block's link and the confirmations come with it. An older block follows nothing: its next block and confirmations are as of the page's load.

#### The block strip's past

The home page's mined lane goes on to the right through every block down to block 0, loaded as the visitor scrolls (`pages/home/past.ts`, drawn by `BlockStrip.tsx`).

- **One lane, a window over it.** Every slot has the same pitch (`--tile-w` plus `--tile-gap`), so the lane is as wide as all its blocks and holds only the tiles near the view: those in view and `OVERSCAN` (6) beyond each edge, each after a margin of the empty slots before it (`--skip`). The newest tile and a focused tile with its two neighbours stay in the page wherever the strip is. In the DOM: 24 mined tiles at most on a 1,440 px desktop, 17 on a 390 px phone, measured. Before the strip is laid out it holds the live list's ten. The lane is laid out 200 slots past the deepest one seen, so a fling never meets its end, and stops at `MAX_DEPTH` (50,000 blocks, about a year) with a link to the Blocks page, because browsers cap an element's width near 17.9 million px.
- **Pages.** Older blocks come from `GET /api/v1/blocks/:start_height` ([`API.md`](API.md#blocks)), 15 a page, from pages of fixed heights asked for from their top (from 104 down to 90, from 89 to 75), so one request serves every visitor and is cached a day once settled. One page is in flight at a time: the one nearest the middle of the view that misses a block within the view or `LOAD_AHEAD` (30) blocks past its far edge. A server without a block table, or a page it has not indexed yet, is asked of the node's `/blocks/:height` instead (ten a page, from the highest block missing). A page that fails is one dashed run in the lane with its error and Try again, its note kept in view while any of it is; it is not asked again until then.
- **Memory.** Blocks more than `KEEP` (90) beyond either edge of the view are let go, so the page holds at most about 260; coming back to them asks again, which the browser or the page-wide answer cache (256 answers) usually serves. A long scroll of 2,000 blocks with the wheel (desktop and phone width, Chromium) drew every frame within 34 ms, with 136 requests and the JS heap from 3.8 to 5.7 MB.
- **Fee facts.** The live list's come as before. Older tiles' come from the batch summary route once the strip has stopped scrolling for `SETTLE_MS` (250 ms), for the older tiles in the page only, so a fling asks nothing; a tile whose facts failed keeps its gauge until it leaves the page and comes back.
- **The live edge.** At "now" a new block crosses the line as before, and the tiles it moves past the live list's ten glide on into the past instead of fading. When the "now" line is out of view, a new block, a reorg or a refetch plays nothing and moves the scroll position by the change in the tip, so the tiles in view stay where they are; the announcement is still made. A reorg below the live list (its oldest block's parent is not the block kept below it) drops everything kept below it.
- **Moving it.** No scrollbar: a mouse drags it and a flick glides on (`components/dragScroll.ts`, rules in [`DESIGN.md`](DESIGN.md#space-shape-and-layout)), a touch screen swipes, and a wheel, a trackpad or the keys move it as before. Every way moves the scroll position, so the window and the pages follow it alike. A drag scrolls by each step of the hand rather than from where it began, so the shift that keeps the view in place when a block comes is kept, and that shift, a key or "← Now" ends a glide.
- **Back to now.** While the line is out of view a button, "← Now" (named "Back to now"), sits in the strip's head, a thumb high on touch screens without changing the head's height. It glides back when the line is within three widths of the view and motion is welcome, and jumps otherwise. Activated from the keyboard, it moves focus to the newest tile.
- **Keyboard and readers.** Tab and Shift+Tab walk tile by tile into the past and back, the strip following focus. A focused tile stays in the page however far the strip is scrolled, so focus is never lost. Home on a tile goes back to now and focuses the newest block. Each tile carries its place among all the blocks (`aria-posinset`, `aria-setsize`); loading, pages and scrolling announce nothing.

#### Following live data

How a page keeps a fetched answer current from a topic. The address page once missed a payment for good in each of the two orderings below, and so could the transaction page, the newest block's page and the replacements list; `e2e/live.mine.e2e.ts` and `e2e/address-live.mine.e2e.ts` build each ordering on purpose on regtest, for every page that follows a live event with a request. A new page follows the same three rules:

1. **Listen from the first ask, and treat the topic's first message as news.** It is the state as it is now, so anything that happened between the page's first answer and its subscription taking effect is in it: compare it with the answer, never take it as "the watch has started". Better still, subscribe first and ask once it has come (the address page). A listener added while another part of the page already follows the topic gets no first message (`lib/live.ts` replays nothing), so mount it with the first ask, not once the answer has come.
2. **A request a live message prompts skips the browser's cache:** pass `fresh: true` to `fetchApi`, `fetchApp` or `fetchStamped`; `createApi`'s `refetch` does it by itself. Our answers that change with an event are `max-age=1`, and the browser shares its HTTP cache between tabs: a copy kept from the second before the event is the old answer, and a page that takes it for the new one has caught up with nothing and stops asking. It adds no request: the ask the event prompted was going to be made anyway, and only a stale copy is refused. A first load does not need it.
3. **Decide that you have caught up from the answer, not from having asked.** Where a server-side cache can trail the event, compare the answer with what the event said (a height, a chain-tip stamp, a status) and ask again a few times: the block strip and its one-second tip cache (`STALE_RETRY_MS`), the difficulty panel's stamp, the address page's catch-up.

4. **An answer asked again rebuilds only what changed.** A list's rows keep their elements for as long as they are given the same objects (`DataTable` keys a row by its object), and each answer is parsed into new ones, so a page that hands the new objects on rebuilds every row on every ask: a reader loses the focus in a row and a note they were sent to, and a browser test loses the row it holds ("Element is not attached to the DOM", seen once in `tables.e2e.ts`). The address page's two lists, asked again each time its topic reports a change, keep the object already held for an item whose answer is the same in every field (`steady` in `lib/steady.ts`, compared field by field and exactly, never by a digest, so a field a later answer changed, a block or an input the node has since pruned, is never hidden behind the old object; a page loaded earlier and not asked again is the very object held, and is not compared at all): a payment arriving rebuilds no row but its own. A cell is still redrawn when a row is put in above it, since `DataTable` hands each cell its row's place in the list.

Pages whose topic carries the whole state (`mempool`, `projected`, `transactions`, `fees`, `projected-txs:N`, `tx:` positions) ask nothing on an event and need none of this. Summaries and audits are fixed by their hash: a new block's summary is served only once its audit is decided, so it is cached for good from its first answer.

### Chain text

What people wrote on the chain, read in the browser for the transaction page's cards and inspector (`pages/tx/chaintext.ts`) and the block page's tag (`coinbaseTag` in `pages/block/chain.ts`). All of it is attacker-controlled: plain strings for text nodes, hidden and bidi characters made visible.

- **A coinbase reads as its words,** one rule for both pages. Pushes are read one by one, so their length bytes never show, and from the first byte that pushes nothing the rest is read as it is (F2Pool's "七彩神仙鱼" is not a push). A run of visible characters is a word when it is 7 bytes or more with at most one rare punctuation mark in 8, and has five letters or digits in a row, two groups of three around `.`, `/` or `-`, two of two around a space, or three letters outside ASCII; merged mining's magic (`fabe6d6d`) never starts one. A lone stray mark at a run's end and a letter or two outside a tag in slashes are dropped; reading stops at the first run of 8 hidden characters after the words. A coinbase with no words keeps the earlier form: every visible character, dots for the rest. `fixtures/coinbase/mainnet.json` holds 84 mainnet coinbases from 2009 to 2026 with how each reads, and the test checks them all and that random bytes read as words about once in 700 runs of 20. Its limit: a stray character beside a tag that is not in slashes stays ("Mined by AntPool616 Z").
- **OP_RETURN text** is its data when it reads as text (`isText`: valid UTF-8, at most a fifth escaped); otherwise the card names its size.
- **An inscription** is the first ordinals envelope in the tapscript of a taproot script-path spend (the item before the control block, past an annex): `OP_FALSE OP_IF "ord"`, tag and value pushes (1 is the content type, 9 the content encoding, others skipped), an empty push, the body's pushes, `OP_ENDIF`. Anything broken (a push past the end, an opcode that pushes nothing, no `OP_ENDIF`) is no inscription. The reader takes at most 10,000 script steps and keeps the first 128 KiB of the body. Its text is shown when the content type is `text/*` or `application/json`, it is not compressed, and the body reads as text; anything else is named by type and size, never decoded or drawn.

### Lookalike addresses

Address poisoning: someone grinds an address whose ends agree with one the reader uses (their own, or one they paid), puts it in their history with a small payment, and hopes it is copied from there later. The address page's history (`History`, so an ordinary address and a kept one whose whole history the server pages) marks a row whose transaction names a lookalike with a caution note under it, and leads the page with a notice that says so (`pages/address/lookalike.ts`, `LookalikeWarning.tsx`, `LookalikeNotice.tsx`; the look is in [`DESIGN.md`](DESIGN.md#address-not-in-the-prototype)). It says the address "may be" poisoning, never that it is.

- **What looks alike.** Two different addresses of one kind (their type from `recognise`, their network prefix and, for bech32, their length, which tells P2WPKH from P2WSH) that agree on characters right after the type prefix (`1`, `3`, `m`, `n`, `2`; `bc1q`, `bc1p`, `tb1q`, `bcrt1q`, …) and on their last characters. Pay to anchor, one fixed address, is left out.
- **Case.** Compared in lower case. Bech32 has one case. Base58's 58 symbols fold into 35 classes (nine digits, 26 letters: only `i` and `o` have no capital, only `L` no small letter), which a glance mixes up and an attacker can grind more cheaply; two random base58 characters fold alike with chance (23 × 2² + 12 × 1²) / 58² = 104 / 3364 ≈ 1 / 32.3, about bech32's 1 / 32, so one set of thresholds serves both. The mainnet case the rule was checked on needs it: `1PwjRJEU…eYVzXU` agrees with `1PWo3JeB…fsVzXU` on `PW` only without case.
- **Against the page's own address:** 2 characters after the prefix and the last 4 (`OWN_HEAD`, `TAIL`). Six characters at about 1/32 each: 32⁶ ≈ 1.07 × 10⁹, against each of N addresses in the history, so 10,000 addresses give a false alarm about once in 100,000 pages. (A 34-character P2PKH address's character after `1` spans only about 23 symbols, which at most doubles that.) The mainnet lookalikes it was checked on agree exactly this far: 2 and 4 without case, about 30 bits, a billion tries.
- **Between two other addresses in the history:** 3 after the prefix and the last 4 (`PAIR_HEAD`), and only when they appear in different transactions: the attack imitates an address paid elsewhere, and a mainnet transaction carries sixteen vanity addresses (`bc1qmullah0ut…5370`) ground to resemble one another and nothing the reader used. Every pair is compared, N² / 2 of them, so the rule is stricter: 32⁷ ≈ 3.4 × 10¹⁰ gives 5,000 addresses a false alarm with chance 3.6 × 10⁻⁴, 20,000 with 6 × 10⁻³. The own rule's 2 and 4 here would be 0.012 at 5,000 and 0.17 at 20,000.
- **Why these ends.** Every short form the site shows keeps an address's last eight characters (`Hash`'s `fit`, in lists and the flow diagram; 8 and 8 elsewhere), while its head gives way to room, down to two characters. So the tail must agree, and an address that agrees with everything a short form shows (`bc1q` and four, and the last eight) is caught well past the thresholds. Addresses that agree only at the start are not marked, however long the start (mainnet's `1PWo3JeB9jr…` has five in its history that share nine or ten leading characters with it): every short form shows their last eight differ.
- **What it knows.** Only the pages loaded: the page's own address against every address its loaded transactions name (inputs' previous outputs and outputs), and those addresses against one another. A lookalike whose twin is on a page not yet loaded is not seen; "Show 25 more" works out every loaded row again, so an earlier row is marked once a later page brings its twin. A row is never marked for naming the page's own address, which every row does.
- **Bounded.** Linear in the addresses named: each is read once and bucketed by its agreeing ends, and a few addresses stand for a bucket of any size, so a transaction of thousands of dust outputs ground to one pair of ends costs no more per address. Measured in V8 (Node 24): 10,000 addresses 16 ms, 100,000 175 ms, 100,000 in one bucket 144 ms. A standard transaction carries at most about 3,200 outputs, so a page of 25 rows is milliseconds.
- **What it shows.** At most two pairs a row, then how many more; each pair the address in this transaction over the one it resembles, whole, with the agreeing ends bold and underlined and the middle quieter, and a sentence for screen readers saying where they agree. Text nodes only, and no link or copy button in it: it is the one place not to copy from.
- **The notice at the top.** Above the totals and outside the tabs, so a reader who never scrolls, or reads the unspent outputs, still learns of it. The page works the lookalikes out once (`AddressBody`, from the transactions `History` reports loaded, both pages and refreshes) and hands the one answer to the notice and the rows. It counts the transactions that name one, honest about what was checked: "of the 25 transactions loaded so far" with "Older transactions are checked as you load them" while the history can load more, then "of the 73 transactions in the history", which holds whichever view is showing. Whether it can load more is the history's own word (a short last page, or a later page that answered empty), never the totals, which are another answer and can be older or newer than the list; and the count is said of the list, not of the address. A kept address's history lists confirmed transactions only, so there it says "confirmed transactions", once every row counted is confirmed (as an address becomes a kept one, its mixed list shows until the kept list answers). It says what the addresses do ("starts and ends like this one"), not why: a chance match looks the same, and the caution under it says "may be". The notice goes when its history does (a kept history the server dropped). A lookalike of the page's own address leads it ("Someone may be imitating this address") and is shown whole beside the address, its agreeing ends marked, then how many more there are: it is the one a reader may take for their own anywhere, wallet included, and a short form would show exactly the ends that agree. A lookalike of another address only counts, and says one of each pair may imitate the other: neither is known to be the copy, both rows are counted, and the row notes show the pair. One button ("Go to the transaction", or "Go to the first of them") takes the reader to the newest marked row: back to the transactions view if another is showing, the row scrolled clear of the sticky header (smoothly unless reduced motion is asked for), focus on its note, which takes focus but is no tab stop. One button, not next and previous: each marked row's note is in the list itself. Screen readers hear its heading once, from a polite live region present from the start, never again as the count changes. It comes with the first history page, in the same render as the rows, so it moves the totals, the chart and the history down by its height once that page answers (on regtest 4 to 11 ms after the totals); a history without a lookalike draws exactly what it did before (its screenshots are byte-identical).
- **The transaction page, from a marked row.** A marked row's links (the txid's and the whole row's) carry that row's findings to the transaction page in the history entry's state (`lib/lookalike.ts`: `handoverState`, the `state` of `Hash`'s `linkState` and `DataTable`'s `rowState`), never in the URL, where a copied link would share the reader's address and the server's request log would keep it. Carried: the transaction and network it was made for, the page's address, and for each lookalike in that transaction the address, the address it resembles, whether that is the page's own, and how far they agree (the type prefix, head and tail), the page's own first, at most 64 (`HANDOVER_MAX`, about 200 bytes each on each of the row's two links), and how many the row had. The transaction page reads it as input (`readHandover`): the state must be an object whose `lookalike` key holds exactly that shape (the router's own keys beside it are ignored), made for this transaction's txid on this network, a list of 1 to 64, a count no smaller than the list and larger only when the list is full, addresses of a kind the rule compares and at most 90 characters. Each finding is held to the rule itself, whose pieces (`form`, the thresholds, the agreement counts) live in `lib/lookalike.ts` for both pages: its address is among this transaction's inputs' previous outputs and outputs; neither address is the other nor the page's address (a bech32 address in either case is one address, base58 is compared as written); `own` is said exactly when it resembles the page's address; the two are of one kind and agree on the ends the rule asks of that sort (2 and 4 for the page's own, 3 and 4 for another); and its prefix, head and tail are exactly where they agree. Anything else is dropped without a word; with nothing left the page is as it always is. That the history had more than are marked is said only of a full list whose every finding holds, and only while the count is no more than the addresses of a kind the rule compares that this transaction names beside the page's own: past that the transaction names too few such addresses for the count to be true, so the count is not a row's and the sentence is left out, the findings kept. Within it the count is taken at its word: whether an unmarked address has a lookalike elsewhere in the history is not something a transaction can say. It then shows a notice above the summary, in the address page's look and words ("Someone may be imitating the address you came from" or "This transaction names a lookalike address"; what the addresses do; at most two pairs whole with their agreeing ends marked, then how many more; "may be address poisoning", check every character; and that it shows because the reader came from that history, as this page looks for none itself), heard from its own polite live region when it shows, and cleared when it goes (another entry for the same transaction without the state), so Back to the entry that carried it says it again. Each lookalike is marked where it appears: its flow card takes the caution rule and the word "Lookalike" with the triangle ("Lookalike address: check every character" aloud), and its inspector shows it whole with the agreeing ends marked, still a link with a copy button now named "Copy lookalike address" (its tooltip too), and under it what it resembles, whole, and the advice. It runs no rule of its own: within one transaction the pair rule would flag a batch of vanity addresses ground to resemble one another. Only a click from a marked row (the router's navigation) carries it, and back, forward and a reload keep it, as the browser keeps a history entry's state (entering the same URL again counts as a reload in Chromium); a link opened in a new tab or window, pasted or shared, or any other way to the page shows nothing new, and the page is drawn exactly as before.
- **Not covered:** the newest-200 list of a kept address whose whole history the server does not have (its ledger rows name no addresses), and a large address's unconfirmed list (`Large.tsx`).

### Privacy check

What a transaction shows anyone who looks at it, as readings an observer makes from its shape (`lib/privacy.ts`, `checkPrivacy`). One module for the transaction page, Broadcast and the decoder: it takes the `Transaction` each already holds, with its inputs' previous outputs, and returns findings as data (which finding, the inputs and outputs it concerns, its reasons and the values a sentence needs); the words are the pages' own. These are heuristics: a finding says what an observer could conclude, never what the sender did. Addresses and scripts are attacker-controlled and only compared, as keys of a `Map`.

- **What every rule leaves out.** A coinbase is not checked. OP_RETURN outputs and pay to anchor (`51024e73`, one fixed script anyone can spend) take no part in any rule, and an input spending an anchor counts as neither an address nor a coin that funds the transaction. "Paying outputs" below are the rest. An address is its script, compared in lower-case hex.
- **Address reuse.** Every address that appears more than once among the inputs and paying outputs: an output paying an address an input spends from, several inputs from one address, or one address paid twice. Two inputs from one parent transaction at different addresses are not reuse. Each entry names the script by its address, or by its hex when it has none (bare multisig, P2PK, an empty or nonstandard script), and `isAddress` says which, as the pay-back reading's does, so a page never has to tell them apart by the string. **What it cannot see:** reuse in earlier transactions, the commonest kind. That needs each address's history, one request per address, so it is not checked, and a page that shows the check says so.
- **Which output is change.** Four readings, each pointing at one output as change. Pay-back outranks the others: that output goes back to someone who signed for an input, where the others guess at a wallet's habits, so when it applies the finding is `change` at its output, the readings that agree are kept as further reasons and those pointing elsewhere are dropped, neither shown nor counted as a dispute. Without a pay-back, when the readings all point at one output the finding is `change` with each as its reason; when they point at different outputs it is `change-disputed`, and no output is called change. A `change` finding names the other output as the payment only when there are exactly two paying outputs; a disputed one names neither.
  - *Pays back to an input's address:* exactly one paying output pays an address an input spends from, and at least one other output is paid. When several outputs pay back (a marketplace trade paying each seller back, or a split to one's own address) no change reading runs at all, and there is no `change` or `change-disputed` finding: those outputs go back to people who signed, so there is no single sender's change to find. The pay-backs are reuse, nothing more.
  - *Round amount:* exactly two paying outputs, one round and the other not a multiple of 1,000 sats (`RAGGED_UNIT`); the other reads as change. Round is at least 10,000 sats, a multiple of 10,000 (`ROUND_UNIT`), with at most two significant digits (`ROUND_DIGITS`): 1,200,000 is round, 1,230,000 is not. Not when both are round. It knows only amounts round in bitcoin; a payment round in dollars is invisible to it.
  - *Script type:* exactly two paying outputs, every funding input of one type, and exactly one output of that type too; that one reads as change. Not with inputs of mixed types, nor when both outputs match. Esplora's `unknown` type covers scripts of different kinds, so it never counts as a match.
  - *Unnecessary input:* exactly two paying outputs and inputs from at least two addresses; the smaller output is less than the coins of the smallest address and the larger output is not, so the smaller reads as change. An address's inputs count as one coin, their sum: a wallet that spends every coin of an address together (Bitcoin Core does for a reused address) adds nothing it did not need, and counting each input alone made this reading contradict an obvious pay-back in 6 of 20 disputed findings on mainnet. The inequality, smaller output < that sum ≤ larger output, is all it states. It does not say the larger output needed every coin: with 103,000 and 302,000 sats in and 100,001 and 300,001 out it fires, though 302,000 alone would pay 300,001. It suggests which output is the payment only if the wallet would not have added a coin it did not need, and some wallets do, on purpose; the weakest of the four.
- **Possible CoinJoin.** At least 3 paying outputs of one value (`JOIN_COUNT`), each at least 5,000 sats (`JOIN_MIN_VALUE`) and to a different address, from inputs at no fewer distinct addresses than those outputs, in a transaction where no address is repeated among the inputs, no output pays an input's address, the outputs outside the equal groups are no more than those in them, and there are no fewer paying outputs than funding inputs. Software that makes CoinJoins avoids reusing addresses, each person takes at most one output besides the equal ones, and every CoinJoin seen on mainnet (15 in fifteen blocks) paid more outputs than it spent inputs. Each condition keeps out something that looked like one: a custodial split of three equal outputs from three addresses, one of them spent from three times (`aa213508…`); a marketplace trade paying equal amounts back to its sellers (`a3582ef2…`); a payout of five equal outputs and one change from 24 fresh deposit addresses (`a96fd879…`); three equal outputs among 132 from four inputs (`d8aaa9f4…`). Every group of 3 or more equal outputs is reported, the largest first. A finding, not a fault. It switches the change readings off, as a CoinJoin has no single sender; the conditions already leave no change reading to make (3 paying outputs, none paying back), so this is a guard for thresholds changed later, and no test can reach it.
- **Spent together,** for a transaction not yet sent (`UNSENT_ONLY`: Broadcast and the decoder show it, the transaction page does not). Two or more inputs whose previous outputs are known and are not anchors, and no CoinJoin: spending coins together suggests they have one owner. Only those inputs are listed and counted; an input whose previous output is unknown may be an anchor, so it never makes up the number, and when the known ones are too few to decide while some are unknown, the check is in `notRun`. It carries how many distinct addresses those inputs spend from, and `noChange` when one paying output takes everything. One input to one output is no finding: an observer learns almost nothing from it.
- **When part is unknown.** An input's previous output is unknown when it is `null` (the node lacks it) or absent (past the check route's first 100 lookups, [`API.md`](API.md#checking-a-transaction), or a parent the node no longer stores). The input list itself is missing (`inputsMissing`) when a transaction that is not a coinbase lists no inputs. That is decided from the data, not from the node's `pruned` flag: rbitcoin v0.9.2 sets it when a transaction's scripts and witnesses are gone, and then lists every input, with its previous output where the parent's outputs are still stored, or no inputs at all, never some of them. Then `unknownInputs` lists the unknown inputs, and `notRun` names each check that applies but did not run because it needs every input: CoinJoin, pays back, script type, unnecessary input, and spent together as above. Round amount needs only the outputs and still runs, unless an amount or a total fails the check below. Reuse runs on what is known. `unreliable` names the findings whose presence the missing data could change, and only those: reuse while any input is unknown; change and disputed change while a reading that could apply did not run, unless two known pay-backs (or one, with every input known) already settle it; CoinJoin unless a repeated input address, a known pay-back or fewer than 3 paying outputs rule it out; spent together when it did not run, or when it is shown and a CoinJoin, which would remove it, is still open. The list is conservative: it never omits a kind the missing or invalid data could change, and it may list one that data could not in fact change (two known inputs, one unknown and three unequal outputs list disputed change and CoinJoin, though neither can be reported); a reader told once too often that a finding may be incomplete loses less than one told once too seldom. What a finding says is true of the data that is there, and none is made from data that is not.
- **Amounts are checked first.** An amount must be a whole number of sats, at least 0 and at most the 21 million BTC supply (2,100,000,000,000,000), and held exactly by a JavaScript number. The decoder's check route writes amounts from the raw transaction's bytes, so anything a `u64` holds can arrive: 2⁵³ and 2⁵³ + 1 read as one number. The totals are held to the same: the outputs together, and the inputs whose values are known together, may not pass the supply, whether or not every input is known, and when every input's value is known (anchors included) the inputs together must cover the outputs; a zero fee is valid, as is a zero-value output. The sums stop once they pass the supply, so they stay exact. If any amount or total fails, the rules that read amounts (round amount, unnecessary input, CoinJoin) do not run and are in `notRun`, and `unreliable` names what that could change, by the rule above. Reuse, pays back and script type read only scripts, and still run. `amountsValid` says whether the amounts passed this check (true for a coinbase, which is not checked), so a page can name bad amounts as a cause of a partial check without inferring it.
- **Bounded.** At most n log n in inputs and outputs: each check is one pass with maps keyed by script or value, and the groups of equal outputs (at most a third of the outputs) are sorted. Measured in Bun: 5,000 inputs and 5,000 outputs 4 ms, 50,000 of each 37 to 46 ms across runs. The tests check what three shapes of 5,000 outputs answer: one value, 1,666 groups of three equal values (the most groups to sort), and every input and output on one address. Their speed, under 50 ms of processor time each on a developer's machine (`lib/cost.ts`), is a benchmark that runs on request (from `web/`, `PRIVACY_BENCH=1 bunx vitest run src/lib/privacy.test.ts`): on a slow CI runner one took 54 ms, with nothing wrong in the code.
- **Tested** on 29 mainnet transactions and one signet in `fixtures/privacy/` (two that fire and the near misses of each reading, three clean, several at once and a disputed one), on every threshold's boundary, and on whole blocks (November 2026): of 18,850 transactions in mainnet blocks 976,788 to 976,793, 44.0% show nothing on the transaction page and 38.5% nothing before sending; reuse fires on 42.8%, change on 47.8%, disputed change on 21 (0.1%), CoinJoin on 10 (0.05%), spent together on 24.5%; the slowest took 0.7 to 1.9 ms, a different transaction on each run (pauses in the runtime, not a shape that costs more). Signet (blocks 331,764 to 331,766, 379 transactions) shows more reuse (74%) and more change (59%), much of it one faucet-like wallet paying itself back; no disputes. Blocks from the node always carry every previous output, so none was partly checked; that case is tested on recorded transactions with inputs taken away. Twenty findings of each kind read by eye found none wrong, after the two refinements above (counting an address's inputs as one coin, and the last two CoinJoin conditions) removed the ones that were. Before pay-back outranked the others it was the right reading in 14 of 20 disputes read; since, the 21 mainnet disputes left have no pay-back, and each is two or three guesses at a wallet's habits that genuinely disagree (script type against unnecessary input in most).

**On the page.** The words are all in `pages/tx/privacytext.ts`, pure functions from a finding to its title, sentences and reasons, and from the findings to the marks on the flow's cards; `Privacy.tsx` only lays them out. A sentence is plain text and addresses; an address is set as a text node (`shownAddress`): cut to its first and last eight characters, each hidden character (controls, format and bidi characters, private use, unassigned, line and paragraph separators, as the block page's tag defines them) a replacement character; whole in its title up to 128 characters, each hidden character written as its code point (`\u{202E}`) and a backslash as two, so two different strings never share a title. Never as markup. (The site's `Hash` shows an address as it comes; making it do the same everywhere is a follow-up.) The look is in [`DESIGN.md`](DESIGN.md#transaction).

- **The transaction page** works the check out with the page itself (`TransactionView`'s `Body`), from the same answer the flow draws, so it arrives with the cards. An output card's meta line has its spent link's height (24 px) from the start, and the status its width: an unseen "Being spent", its widest words, shares the status's cell, so the line wraps the same before the answer and after in any font (CI's prose font is wider than a Mac's; the test runs in the wide stand-in at 320 and 360 px). So the spends arriving later move nothing; before this, every page grew 7.8 px a spent output when they did, privacy check or not. Under the flow, in its panel: "What an observer can read" and a finding each, or one muted line ("Nothing in this transaction's shape stands out."), then "What this checks". Findings for an unsent transaction (`UNSENT_ONLY`) are not shown, nor named among what could not be checked. A coinbase shows nothing.
- **Broadcast and the decoder** (`CheckedTx`) show the same before the action (the Broadcast button, or the decoder's link to it, which `CheckedTx` places after the notice) as a neutral notice, "Once it is sent, anyone can read this from it", with coins spent together too, and close with "It is not sent yet: a wallet can still change which coins it spends and where the change goes." With nothing to show it is still whole: the heading, "Nothing in this transaction's shape stands out.", the closing line and "What this checks". It says "not sent yet" only for a transaction the page has never tried to send. From the first press on, whatever came back and however often the result is drawn again (`pages/push/attempted.ts` keeps the transactions pressed, by network and txid, for the life of the page), it reads as the transaction page's, with nothing for an unsent transaction on it or on the cards, and claims nothing about whether it was sent: the button's own line says what the broadcast returned. Telling a refusal that kept it out of the mempool from one that did not needs more of the node's admission rules than a page should hold. Not for a transaction the node already has, which is sent. The Broadcast button is unchanged: these are readings, not faults.
- **Marks on the cards,** through `Flow`'s `marks` prop, keyed `in:N` and `out:N`, at the end of a card's meta line: "Reused address" on every input and output at a reused address, "Reads as change" and, with exactly two paying outputs, "Reads as payment" for an undisputed change finding, and "Equal amount" on a CoinJoin's equal outputs. A disputed reading and coins spent together mark no card. Each mark is the eye and its words; the eye is hidden from screen readers, so a card reads its words.
- **Tone.** Caution (`--color-caution`, the filled eye) where something is given away: reuse, change, a disputed reading, coins spent together. A CoinJoin's shape is neutral (the open eye, the text's colour): not a warning, not praise.
- **Very large transactions.** A mark is looked up per card drawn, and the flow draws ten, then a hundred more at each press, so no more marks than cards are ever drawn. Sentences list up to five inputs or outputs by number and count past that ("65 inputs"); reuse says three addresses and counts the rest.
- **Partly checked.** When the report has unknown inputs, a missing input list, checks not run or findings it calls unreliable, the page says so in its own lines after the findings: "Only part of this transaction could be checked.", then each cause with the checks it held back ("What input 100 spends is not known here, so these were not checked: …", "Its inputs are not listed here, …", "Some of its amounts cannot be right (…), so …"), and "What it shows about … may be incomplete." from `unreliable`, which is conservative, hence "may". Amounts are named as a cause exactly when `amountsValid` is false. Such a transaction never reads "Nothing … stands out"; with no finding it says "Nothing was found in the part that could be checked."
- **Checked on mainnet** (November 2026): on 66 transaction pages (every example the rules were built from, thirty at random from block 976,804, a disputed one, a CoinJoin and the largest of two blocks) each sentence and each mark on the first ten cards matched the rules' report, both ways: 158 sentences and 159 marks. A real 890-input consolidation showed its section 230 ms after the page started, and a 4,986-output one (a CoinJoin's outputs repeated, served to the page) 126 ms, drawing 10 marks and naming 3 of 277 reused addresses; neither had a main-thread task over 50 ms.
- **Every form of sentence it can say** is held to its exact words by `privacytext.test.ts`, built from reports the real rules make: each finding kind, each reading agreeing (one to four) and disputed (two and three), each cause of a partial check alone and together; a disputed pay-back, which pay-back outranking the others makes unreachable, is not. Each says what its rule established and no more: "reads as" and "suggests" for a heuristic, what an observer may read and never who owns, controls or sent anything; reuse states that the locking script matches, and calls a reused script with no address a locking script, as the rules say (`isAddress`); the smallest-coin reading states its comparison of what each address spends, never that an output could not have been paid.

### Command palette

A second way in beside the header search, in `palette/`. ⌘K on Apple's keyboards (read from the user agent) and Ctrl K elsewhere open it from any page, even from a text field, and press again to close; `/` still focuses the header search. The header shows the shortcut as a key-cap button, "Go to", where the search's cell has room for both (46em to 65em, and from 78em; `palette.e2e.ts` measures that the search's placeholder is never cut for it). Wherever the hint is hidden (phones, and the widths just above each of the header's breakpoints), focusing the search shows "Go to a page, pool or date" hanging from the header's bottom edge, below every header row at that width (the sections' row too, on a phone), lined up under the search field: it moves nothing and hides nothing, comes next after the search (and its scan button) in the Tab order, stays while it or the search has focus, and hands what the search holds to the palette. It never lies over a header control, and stands aside while the search's own list or answer is shown, or the network menu is open beside the search. The header's sections stay in place, reachable by a tap and in the Tab order both ways. It may cover page content just under the header while the search has focus: a decision, as a dropdown of the focused search, which goes when focus leaves both the search and it. `palette.e2e.ts` sweeps 320 to 1,600 px for one way in or the other, and for no header control under it, scrolled and at large text sizes.

- **Opening and closing** are one state machine, `opener.ts`, which `PaletteKey.tsx` feeds and draws. States: `idle`; `loading` (the code downloading, with whether to open on arrival); `open`, the only state in which a row runs; `closing` (the fade, with whether to open again after it). Events: `press` (the shortcut, the hint or "Go to"), `escape` (Escape, a press outside, an action done), `arrived` and `failed` (the code), `navigation` (any, Back included, from `useBeforeLeave`) and `closed` (the fade has ended). A press while loading or closing toggles the intent, Escape or a navigation withdraws it, a failed download returns to `idle` so the next press tries again, and each opening is a fresh palette. `opener.test.ts` walks every event sequence up to four long. The shortcut ignores a held key's repeats and keys an input method is composing.
- **Cost.** Only `PaletteKey.tsx` (the listener and the two buttons, about 1 KB) is in the shell. `Palette.tsx` and its ranking (`match.ts`) are a lazy chunk, sharing `search/search.ts` with the header search, fetched on first open or a little before it: when a pointer rests on the hint, the hint has focus, or "Go to" is pressed or focused. Loading is one shared operation (`loader.ts`): it asks again for each of its own files that failed before (`retryFiles` with a test of the address, [above](#when-a-pages-files-fail-to-load); a page's failed files are left for the shell), imports the code, and checks that `Palette.css` is applied (a probe rule of its own); a warm-up and a press join the one in flight, and it counts as arrived only when all of that succeeded. Any failure tells the opener `failed`, so the next press starts afresh: a stylesheet that failed offline never leaves the palette unstyled.
- **What it finds.** Everything the header search reads, through the same `classify`, `describe` and `createSearch` (an id is looked up as the search looks it up, and a miss is said in its row), and Lightning nodes by name with each alias's key beside it. Mining pools by name from `GET /api/v1/mining/pools`, asked once per network on first need. A date (`2024-04-20`, with or without a time, or with the month in words; never `04/05/2024`) read in UTC, as every time on the site is written, as the end of that day or minute, and answered by `GET /api/v1/mining/blocks/timestamp/:t` (whole seconds) with the newest block by then. Its `404` means the server's history holds nothing that early, not that no block exists, and the row says so; a failure is said as one and asked again on Enter. A date before the first block opens block 0. The pages in `pages()`, which a unit test holds to the route table, and actions: each other network the server has on, and the other theme. Empty, it lists the pages and actions. It keeps nothing a visitor typed.
- **Requests.** 280 ms after typing pauses, as the header search asks: the pool list once, then one request, the date's block or the Lightning names, each checked after every wait against a generation that an edit, a lookup or closing moves on. Enter on an id or a date starts an explicit lookup on a search of its own (`createSearch`, a second one), which nothing but an edit, a newer lookup or closing cancels: the suggestions' cancelling (a key, the config arriving) never reaches it. "Looking up…" is drawn from the current lookup's record, which the lookup clears in its own `finally`, so no way it ends leaves the row looking. A date's answer is kept by the typed text and its cutoff once that has passed: Enter after UTC midnight asks again for the finished day, though the row's preview, drawn before midnight, still names the earlier block until then (declined in review: a palette left open across midnight is rare). The pool list's request is not aborted (it is shared and kept), only ignored.
- **Ranking** (`score`): the whole name, then its start, a later word's start, a keyword, and from three letters a match inside a word and letters in order. The search's reading and the date lead; the other groups follow by their best row (`orderGroups`: "ant" puts AntPool before a page with the letters in order), the given order (pages, pools, Lightning nodes, actions) breaking ties; "All Lightning results" comes last. The row shown as selected is pinned by its id until the text changes or the reader moves it, the default included when it matched by name (a name's, a word's or a keyword's start, or the search's and the date's rows), so a row arriving later above it never changes what Enter opens. A weak default (letters in order, "All Lightning results") shows while names are still asked for and gives way to the name that arrives: on mainnet, pinning it made "foundry" search Lightning instead of opening Foundry USA.
- **Text from the chain or gossip** (pool names, aliases) goes through `cleanAlias` and into text nodes only.
- **Accessibility.** A native `<dialog>` opened with `showModal()`, so the page behind is inert, holding a combobox with `aria-activedescendant` over a listbox of named groups. Arrow keys, Home and End move, Enter opens, Escape or a press outside closes, and focus goes back to where it was. A pointer selects a row only when it moves. The count is said once typing pauses. `e2e/palette.e2e.ts` and `e2e/a11y.e2e.ts` hold it.
- **The keyboard on a phone** covers the page without resizing it, so the panel takes its height from `visualViewport`, through a custom property in the `style` object.

### QR codes

The address page shows its address (not a public key's page: no wallet pays a scanned key), and a Lightning node's page its connect string, as a QR code (`components/qr/`, drawn as [`DESIGN.md`](DESIGN.md#qr-codes) says). Nothing about it is sent anywhere: the code is made in the browser.

- **The encoder is ours** (`lib/qr.ts`, about 400 lines, no dependency): byte mode with the text's UTF-8 bytes and no ECI header declaring that character set (the pages pass ASCII only: addresses and connect strings), versions 1 to 40, all four levels, the mask with the least penalty. Byte mode only: a bech32 address in capitals would fit alphanumeric mode and a code one version smaller (a taproot address 37 modules a side instead of 41), but the code would then hold another string than the page shows and copies, and a connect string (lower-case hex, `@`) gains nothing.
- **Level Q, and a logo the code can lose** (`components/qr/draw.ts`). Up to version 6 the logo hides a centred square: the largest, up to 30% of the side, under which no Reed–Solomon block loses more than half of the errors it can correct (`damage` in `lib/qr.ts` counts, per block, the codewords hidden), so half is left for the camera. From version 7 a code has an alignment pattern in its middle, and with a logo over it zbar failed every version 10 code we drew, the logo's shapes taken for the pattern. So there the pattern stays, as the block the crab lifts, and the crab hides only the modules round and under it, at the same budget; a version 7 code, too small for that, is drawn as version 8. How a code is drawn follows from the pixels a module gets on the card as it is laid out, which the pop-up measures and measures again when the window changes (`drawingFor` in `draw.ts`): the logo from 4.75 px a module, soft modules and finder pupils from 4.62, and below that a plain code (square modules and finders, no logo), as a dense code on a small card must scan before it looks good. The card is 302 px on a 320 px phone, 318 on wider screens and 254 on a phone on its side (640 or 568 × 320). The bounds are measured against a plain control of the same code at the same size, for versions 2 to 13, all eight masks, two strings each and cards from 240 to 318 px (November 2026): below 4.62 px a module the soft drawing lost 12 to 13 reads per band of sizes that the plain control made, and won 0 to 4; from 4.62 up it lost 0 to 1 and won 1 to 7, the same scatter as the plain control's own misses, which OpenCV makes at up to 7 px a module. The logo's losses above 4.62 were as rare; it starts at 4.75 for margin, as it hides modules too. In the final sweep (cards of 254 to 318 px) the drawing lost 2 of 3,456 OpenCV reads to the plain control, both of one version 7 code that the plain control also failed at two neighbouring sizes, and none in ZBar or ZXing. So a real onion connect string (134 bytes, version 10) has the crab on a 318 px card, soft modules on 302 and a plain code on 254; the longest connect string the node page shows (an address cut at 128 characters, 195 bytes, version 12) is always plain.
- **A node's colour is the operator's choice,** so it is checked twice: the node page draws only a `#rrggbb` it announced, and `inkFor` holds it to 4.5:1 against the card (`--qr-paper`), scaling its light down evenly (hue and saturation kept) until it reaches that, or falls back to `--qr-ink`. It reaches the page as a custom property through the `style` object, as every dynamic colour does.
- **Checked against independent encoders and decoders.** `fixtures/qr/reference.json` holds eight codes from python-qrcode 8.0 with the mask forced, which `qr.test.ts` matches module for module; while it was written, all 160 versions and levels matched at full capacity and with padding. segno 1.6.6 matched only at full capacity: it adds a spare zero byte when the data already ends on a byte boundary, which still decodes. The automatic mask choice differs from both libraries' in some codes (the standard's finder-lookalike penalty is read differently by each); any mask decodes. Screenshots of both pages in Chromium (320 px, 360 px and desktop, light and dark: a legacy, a regtest taproot and a mainnet taproot address; connect strings with IPv4, IPv6 and v3 onion hosts and the longest the page shows; a pale and a dark node colour: 66 images) all decode to the exact string with ZBar 0.23, ZXing (zxing-cpp 2.2) and OpenCV 4.10 (November 2026). OpenCV's detector is the one that shaped the drawing: it misread codes whose finder rings were rounded by a quarter of a module or more, whose lone modules were round dots, or whose crab was drawn at the full scale of its block, and needs about 4 px a module, which is why the card runs edge to edge in the pop-up (at least 296 px on a 320 px screen).
- **Loaded on first use, by the button.** `QrButton` is in the `app` group ([Chunks](#chunks)); its pop-up, the encoder and the drawing (`QrPop`, about 5 KB gzipped) load when a reader first opens a code. The button loads them itself rather than through the shell's boundary, so a failed download leaves the page as it is: the button turns to "Not loaded". Loading and opening are kept apart (`components/qr/load.ts`). The load is one for the page: it asks again for every file that failed (`retryFiles`, [above](#when-a-pages-files-fail-to-load)), imports the code, and checks that the pop-up's stylesheet applies (Vite does not wait for a stylesheet it already has a link for, failed or pending, so an import alone can bring the code without its styles); a press while it runs joins it, nothing cancels it, and only a load that did all three is kept, so after any failure the next press starts afresh. A stylesheet found not to apply is noted as failed (`noteFailedStyle`), so that press asks for it again. Each press only wishes to open: Escape, a second press, a press anywhere else, focus moving elsewhere or leaving the page withdraws the wish and its listeners, and a withdrawn wish opens nothing when the load ends. Focus alone is not the test: Safari does not focus a button it clicks, and a press on blank space leaves focus on the page. In WebKit, which keeps a failed import for the life of the page, a retry fails until the page is reloaded.
- **Placed by its layout size**, not its drawn box (the opening animation scales it), and placed and drawn again whenever the window changes size: a phone turned keeps it open (`openPop`'s `follow`, which takes a resize, and the browser's own scroll just after it, as a new place for the button rather than a reason to close). A scroll by the reader that carries the button away still closes it, and focus then goes back to the button. On a short screen (a phone on its side) the card is made no taller than the room under the pop-up's title, so the whole symbol and its quiet zone are always in view and only the text under it scrolls; there the pop-up may also cover the header, which scrolls with the page on such screens. `e2e/qr.e2e.ts` covers both pages, 320 px with motion on, a failed and a slow download.

### QR scanner

The header search's scan button (`scan/ScanButton.tsx`) opens a dialog that reads a QR code from the camera or from a chosen picture, and hands its text to the search, which looks it up as if typed: the same `classify` and `resolve` (`search/`), never a Lightning name search (`createSearch`'s `run(text, network, false)`), so a code leads where its text would: a code holds an identifier or nothing the site knows (a Wi-Fi login, a menu's address), and the second is said as such rather than searched for as a node's name; a node's code holds its key or connect string. A code the search does not know is shown in the search's answer as "Code not recognised", its text in a `<q>` with control and bidi characters made visible (`visible`, as aliases are) and cut in the middle. What a code holds is attacker-controlled: it is only ever text. A node's connect string (`<key>@<host>:<port>`, what node QR codes hold, ours included) is read as its node, typed or scanned.

- **Reading.** The browser's own `BarcodeDetector` where it reads `qr_code` (Chrome on Android and macOS); everywhere else jsQR (`scan/decode.ts`), a dependency: a QR decoder is 1,000 to 2,000 lines of locating, sampling and Reed–Solomon we would have to write and keep, and jsQR is one package with no dependencies (Apache-2.0, 1.4.0). It is its own chunk, 130 KB (48 KB gzipped), fetched only when the scanner opens on a browser without its own reader. jsQR takes text and edges near a code for finder patterns at some sizes and not others: on 60 screenshots of the site's own address codes (five types, 1× to 3×, light and dark, the pop-up alone and the whole page) one size read 33. So a picture is read up to five ways (`WAYS`: its longer side at 1,024, 768, 560, 400 and 320 px, a few pixels shifted), stopping at the first that reads, which read all 60 (November 2026); the camera reads each frame one way, in turn, about eight frames a second. ZXing's JavaScript port read 48 of the same 60 in one try and is three times the size.
- **The camera.** `getUserMedia` for video only, the back camera where there is one (`facingMode: environment`), shown mirrored when it faces the reader. Only the middle square the preview shows is read (`visibleSquare`), so the scanner never follows a code the reader cannot see; from the moment the picker opens until a picture is read or the picker is closed with nothing chosen, what the camera finds waits; a reader that failed to download stops the camera reading, says so with "Try again", and a picture whose reader then loads restarts it; and a code of nothing but spaces counts as no code. It needs a secure context (HTTPS, or `localhost`); without one, or without a camera, the dialog says so and offers the picture. A blocked or busy camera is named as such, with "Try again". The stream stops whenever the scanner closes: a code read, Escape, its close button, a press outside, leaving the page (`useBeforeLeave`), the track ending, or a camera the browser grants after the dialog closed. The server sends no `Permissions-Policy`, so the camera is the site's to ask for; `video.srcObject` and `createImageBitmap` of a chosen file load nothing by URL, so the Content-Security-Policy needs no `blob:` or `media-src`.
- **Loaded on first press,** as the QR pop-up is (`createLoader` in `components/qr/load.ts`, `retryFiles` for its own files, a probe for its stylesheet): only the button (about 1 KB) is in the shell. A failed download turns the button's name to say so, and the next press tries again; in WebKit, which keeps a failed import, that waits for a reload.
- **Under 360 px** the resting search has no room for the button beside "Search": it shows once the search has focus, which gives the search the whole first row. A press on it never takes focus, so it cannot vanish under the finger in Safari, which does not focus a pressed button; closing the dialog brings focus back to it.
- `e2e/scan.e2e.ts` picks pictures (a transaction ID, a capitalised payment URI, a node's connect string, unknown text, a screenshot of the address page's own code, no picture) and stands in a `BarcodeDetector` for the native path, which Chromium on Linux lacks; `e2e/scan-camera.e2e.ts` films a code with Chromium's fake camera (`--use-file-for-fake-video-capture`, a Y4M drawn by `e2e/qr-images.ts`) and checks the camera is off after every way of closing.

## Transaction grid

`components/txgrid/` draws transactions as a packed map of rectangles in WebGL2: area by virtual size, colour by fee band, the dearest at the top left, one clean block on the floor of the frame as high as the block is full ([`DESIGN.md`](DESIGN.md#the-transaction-grid)). The block page, the projected-block page and the home page (the next block, read-only) use it.

| File | Holds |
|---|---|
| `TxGrid.tsx` | The component (default export, so `lazy()` can load it) |
| `decode.ts` | `decodeTxs(buffer)`: the `/txs` records as `GridTx[]`. Throws `TxsFormatError` (`kind: "version"` asks for a reload) |
| `layout.ts` | `GridTx`, `layout(txs, aspect, capacity)` and `hitTest`. Pure |
| `scene.ts` | Where each rectangle comes from and goes to, and when. Pure |
| `gl.ts` | The WebGL2 program: one instanced draw call, animated in the vertex shader |

**Load it lazily.** It is about 7 KB gzipped and only pages that draw it should fetch it. Import types with `import type`, which costs nothing, and the component with `lazy()` inside its own `<Loading>`, so it never holds the page. Call `.preload()` in the page's `onSettled`, so the code downloads while the data does. `decode.ts` is small and may be imported statically.

```tsx
const TxGrid = lazy(() => import("../../components/txgrid/TxGrid"));

<div class="my-frame">{/* position: relative, with a size: the grid fills it */}
  <Loading>
    <TxGrid
      txs={txs()}                       // GridTx[]: { id, vsize, fee, value?, rate?, coinbase? }
      capacity={1_000_000}              // vB the frame stands for; more than that shrinks to fit
      label="Map of the block's 4 198 transactions, …"   // the canvas's text alternative
      txid={(tx) => fetchApi(network(), `/block/${hash}/txid/${tx.id}`, { as: "text" })}
      lit={litOf(pick())}               // keeps these lit and dims the rest; undefined lights all
      highlight={rowHovered()}          // an id to ring, or undefined
      onState={setGridState}            // "drawn" | "lost" | "unsupported"
    />
  </Loading>
</div>
```

**A whole block** is one array. **Changes** are a new array: the grid matches it to the last by `id`, so keep ids stable (the block index for a mined block, the txid for a projected one) and keep each unchanged transaction the same object (the grid caches its band per object). Squares that stay travel to their new places, new ones drop in, gone ones fade out where they stood, and a change that arrives mid-animation starts from where each square is. For a projected block (`projected-txs:N`, [`WS.md`](WS.md#binary-frames)), make each record `{ id: txid, vsize, fee, rate: effectiveRate / 1000 }`: `rate`, in sat/vB, orders and colors the square by the chunk it is mined in rather than by its own fee, and `value` is left out because the record does not carry it. `BlockTxs` in `lib/projected-txs.ts` keeps that map: apply the snapshot and each delta to it, and pass `[...model.txs.values()]`; order does not matter, because the layout sorts. Keep the grid mounted when the block empties, so the last squares fade out instead of vanishing. A transaction whose fee rate changed is a new object with the same id: it moves. Changes that arrive while the tab is hidden are applied without animation.

- **Layout** (`layout.ts`). An ordered squarified treemap in fractions of a cell: the coinbase, then fee band by band, dearest first, the largest first within a band; each run of rectangles is laid along the shorter side of the space still free and grows while its worst rectangle gets closer to square. Every area is its vsize over the vB a cell stands for (the frame is the weight limit), at least `MIN_AREA` cells, so the rectangles tile one rectangle exactly, as high as the block is full; a nearly empty block keeps at least `MIN_ROWS` of height and is narrower instead. The grid has about 160 000 cells, shaped to the frame in 4% steps, so a frame that changes size by a pixel keeps its picture and is only rescaled. More than the capacity scales everything to fit. A full mainnet block lays out in a few ms, on the main thread.
- **Hit testing** walks the runs (a few dozen) to the one holding the point, then searches it: exact, and for where rectangles are going, not where an animation has them.
- **Instances** are 14 floats: where a rectangle comes from and goes to (x, y, width, height each), its start, duration, curve and colour, and its alpha from and to. The vertex shader mixes them, snaps a rectangle at rest to whole device pixels and leaves a one-pixel seam on any side wide enough to spare it.
- **Colors and motion come from the tokens** at run time: `--fee-1` to `--fee-10`, `--color-text-muted` for the coinbase, the durations and curves. A theme switch repaints; reduced motion leaves only fades.
- **States.** `onState("drawn")` after the first frame; `"lost"` when the WebGL context is lost (the canvas hides; show your stand-in until `"drawn"` comes again on restore); `"unsupported"` when the browser has no WebGL2 (keep your stand-in and say why). Keep a stand-in in the frame until `"drawn"`.
- **Accessibility.** The canvas is `role="img"` with `label` as its name, and is not focusable. Put the same transactions in a list beside it and pass the hovered or focused row's id as `highlight`.
- **Lit and dimmed** (`lit`). Squares `lit` returns false for fade where they stand to `--txgrid-dim` (0.14 in light, 0.2 in dark, `TxGrid.css`), so the block keeps its shape and its fee hint; lit ones keep full colour and grow back into place, leaders first (under reduced motion they only fade). A new `lit` relights with no new layout (`Scene.relight`); a new `txs` lays out as before, each square carrying its alpha. While no more than a tenth of the squares are lit, a second draw call marks every lit square narrower than 5 CSS px: drawn again at least that wide, centred, in a ring of `--color-text`, so a few among thousands are found on a phone. More lit than that, the dimmed ones are the few and rings would only be noise.
- **Measures.** It records `txgrid layout`, `txgrid relight` and `txgrid first frame` with `performance.measure`, for profiling and browser tests.

### Goggles

"Highlight", under the map on the block page and the projected-block pages (not the home page, whose next-block map is read-only): the reader picks kinds of transaction, read from each one's flags ([`API.md`](API.md#transaction-flags)), and the map keeps those lit ([`DESIGN.md`](DESIGN.md#the-goggles)).

| File | Holds |
|---|---|
| `lib/flags.ts` | `readFlags`, `has`, `words`: a flags field as a number, tested as two 32-bit words. No BigInt per transaction |
| `lib/goggles.ts` | `KINDS` (the bits the server sets, the common five first, then by group), `census`, `matcher`, `litOf`, `resultLine`, and the pick: `pick()`, `setPick` |
| `components/Goggles.tsx` | The control: the button, the picked kinds as tags, the result line, the panel |

- **One pick for the visit.** `pick()` is a module-wide signal, so every map on every page lights the same kinds, kept in `sessionStorage` (`goggles`) for the tab: a new visit starts plain, and the pick is never in the URL. A stored value is read strictly (`readPick`): unknown kinds are dropped.
- **Counted once per change.** `census(txs, pick)` counts every kind's transactions and virtual size, what the pick lights, and, in "All" mode, what each kind would leave lit, in one pass: about 2 ms for 16 000 transactions, under 1 ms for a full mainnet block (`goggles census`). The control runs it in a memo of the block and the pick, never per render; the map tests each square with `litOf(pick())`.
- **A live block says nothing.** On the projected page the block changes every 2 s: the shares and the result line follow, but only the reader's own change (a kind, the mode, Clear) is said, once, in a polite region; the result line itself is not live. A share is as wide as its widest figure, so new figures never move a chip under a finger.
- **Open:** a sheet from the bottom up to 65em, the map scrolled to just below the header above it; wider, a panel docked beside the map, over the facts (the map's panel is its positioned ancestor). Non-modal: the map stays live. Done or Escape closes it and focus returns to the button. A kind absent from the block is dashed and `aria-disabled`; in "All" mode one that would leave nothing lit is dashed but can still be picked.
- **Nothing here is chain data:** the flags are numbers and every word is ours.

## Charts

`components/chart/` draws the time series the mining, Lightning and address-balance pages need (the mempool history draws its own plot from the same `geometry.ts` and `scale.ts`), in SVG: a line, a filled area or a step on one value axis or two; percentile bands; and stacked shares. It is written here rather than taken from a library (the comparison with uPlot is in the PR that added it): about 4 KB gzipped, colors straight from the tokens, so a theme switch needs no repaint code.

| File | Holds |
|---|---|
| `Chart.tsx` | The component (default export, so `lazy()` can load it) |
| `scale.ts` | Linear and log scales, round value ticks, time ticks from hours to decades, `formatSi`, `formatHashrate`, `formatShare`, `formatDay`, `describeSeries`. Pure |
| `geometry.ts` | Paths broken at gaps, `stackLayout`, `nearestIndex` and `layerAt` for hit testing, `extent`, `sorted`. Pure |
| `csv.ts` | The chart's data as a CSV file, its file name, and the download. Pure but for `saveCsv` |

**Load it lazily,** as the grid: `const Chart = lazy(() => import("../../components/chart/Chart"))`, call `Chart.preload()` in `onSettled`, and hold its height while it loads (`pages/mining/parts.tsx`, `ChartSlot`, holds `height` + 5.75rem: readout, plot and caption). Import types and the pure modules statically; they cost nothing until used.

```tsx
<Chart
  label="Hashrate and difficulty, the last year"   // its accessible name
  x={times}                                        // unix seconds, ascending
  domain={[yearAgo, now]}                          // optional: the time range drawn
  dataFrom={answer.coverage?.fromTime}             // optional: hatches what is not stored
  height={260}
  left={{ format: (v) => formatHashrate(v), log: "auto" }}
  right={{ format: (v) => formatSi(v, "") }}        // optional second scale
  series={[
    { name: "Hashrate", values: hashrates, draw: "area", format: (v) => formatHashrate(v, 4) },
    { name: "Difficulty", values: difficulty, draw: "step", axis: "right", tone: 2, format },
    // until: a step holds its last value on to this time (the address balance, to now)
    // draw: "step-area" is a step with its area; unit: "BTC" goes after the readout's figure
    // and into the figures' header; marks: true dots each sample while samples are sparse
  ]}
  bands={[{ name: "10th to 90th percentile", lo, hi, tone: 1, format }]}   // optional
  layers={[{ name: "Foundry USA", values: shares }, …]}                     // optional, 0–1
  layerFormat={formatShare}
  time={(t) => `Week of ${formatDay(t)}`}           // optional: how a point's time reads
  summary="…"                                       // optional: replaces the written summary
/>
```

- **Values** are numbers or `null`. A `null`, or two points more than three times the median step apart, breaks the line: missing data is a gap, never a dip to zero. Data with a fixed step passes `gap={step}`, so a single missing step breaks it too. A point alone between gaps is a short tick on a line; with `gap` given it is also a 2 px sliver in an area, which without it draws nothing (the mining charts, unchanged). Points before `dataFrom` do not exist; the part of `domain` before it is hatched and labelled "No data stored".
- **Axes.** `log: "auto"` turns a log scale on when the data spans more than three decades (hashrate over all of history). `zero` keeps 0 in view; `domain` fixes the range (`[0, 1]` for shares). `fee: true` runs the fee colors along a fee-rate axis, as its key. Ticks are round numbers; time ticks step by hours, days, Mondays, months or years, at most one per 84 px. Each value axis is as wide as its longest tick label needs, measured in the labels' font when the chart lays out (regtest's fees read `0.0000002 BTC`), and never narrower than its usual 66 px (58 on the right), so no label is ever cut; `periods.e2e.ts` checks every label stays on its plot.
- **Tones,** never fee colours: tone 1 is `--series-1` (the main series, solid, over an area of it at 14%, drawn only when its axis starts at zero), tone 2 `--series-2`, dashed. A layer with `pool: n` (1–6, 0 for the rest) takes that pool's colour (`--pool-n`). Bands are series 1 at 18% and 36%; stacked layers are shades of it with a seam of the panel between them, the first at the bottom. A layer with `fee: n` (1–10) is amounts in fee band `n` instead, filled with that band's fee color (the mempool's size by fee rate), and can give the readout a `short` name (`0.2–0.3`) while `name` is what is read aloud and heads the table. The layer under the pointer or finger keeps its colour and takes an outline in the text colour while the others fade; the accent is never drawn in a plot, and a tap outside the plot lets the layer go.
- **Notes** (`notes={[{ name, values, format }]}`) are figures the readout, `aria-valuetext` and the table show at each point without drawing them: a count beside a size.
- **The axis** names its first and last moment instead of ticks when the plot is under 420 px wide (`endLabels`), as months and years (`Nov 2020`) when the ends fall in different years and the plot is under 170 px. On a chart under 480 px wide (a container query) the readout leaves out a fee chart's bands except the one under the finger, which has a line of its own held by "Tap a layer to name it" until a finger picks one, so a tap never moves the plot.
- **The readout** sits above the plot at a fixed height and shows the latest point, or the one under the pointer or finger (a tap keeps it). The plot is a `slider`: it takes focus, the arrow keys, Page Up and Down, Home and End move through the points, Escape returns to the latest, and `aria-valuetext` reads the point's time and every figure.
- **Points that are items** (`href={(i) => paths.block(…)}`): a point opens its item on a click, on a second tap within 22 px of the point a finger picked (a 44 px target) (the first only reads it, so a tap never navigates by surprise), or on Enter; each row of the figures links to it and opens it from anywhere on the row. The block health chart uses it.
- **Text alternative.** A summary written from the series (where each went, its lowest and highest) describes the slider, and "Show the figures" opens every point as a table, or the table `table` gives where the points are not all records (a fee's steps). Pass `summary` when the series alone would not say it (stacked shares). A series or band with a `unit` has it in its column's header and bare figures in the cells (a band's range may break before its upper end on a phone, and a band can give a `narrow` name for a phone's header: "Middle 80%"); times that end in UTC say it once, in the header ("Time, UTC"), and on a phone take two lines, the day over the time of day.
- **Samples** (`marks: true`): a series whose points are moments something was looked at gets a dot at each while they stand at least 24 px apart (`MARK_SPACING`), so two looks joined by a line read as two looks. A value whose changes the record dates exactly is a step instead ([`DESIGN.md`](DESIGN.md#charts)).
- **Download CSV.** A chart drawn by this component has the control at the right end of the "Show the figures" line, floated there so the chart is no taller for it (where large text on a narrow phone leaves the two no room on one line, the figures' control goes under it); its label names the chart. The home page's chart hides it with its figures, since its panel's height is fixed, and the mempool page's history draws its own plot and has none. The file is built in the browser from the props, with no request: a row per point, the time as ISO 8601 UTC and as unix seconds, then a column for each series, band end (`low`, `high`), note and layer, in that order, each the raw number (sats, not the formatted BTC) with its unit in the header from `rawUnit` (`layerUnit` for layers). The unit is given at each call, because `unit` names the formatted figure. A gap is an empty cell; joins only change the drawing, so they add no column. Text is quoted (RFC 4180), and a header that starts with `=`, `+`, `-`, `@` or their full-width forms, a tab, a carriage return or a line feed gets a `'` in front so a spreadsheet opens it as text (a spreadsheet that saves the file again may drop the mark, which nothing in the file can prevent). A number is written only when it is finite. The name is `rbitcoin-<network>-<label>-<YYYY-MM-DD>.csv`, in lower-case letters, digits and dashes, because a label can hold a pool's or a node's own words. It is saved through a `blob:` link with `download`, which the CSP allows: a download is a navigation, which `default-src` does not cover. `chart-csv.e2e.ts` checks it in Chromium.
- **Cost.** It draws the paths again only when the data or its width changes, never on hover: 1.5 ms for a year of daily points and 5 ms for ten years, with a line, an area and eight stacked layers. Hovering a 967-point chart holds 60 fps.

### The address balance chart

`pages/address/BalanceChart.tsx` draws an address's confirmed balance after each block as a `step` series held on to now (`until`), with the block and its net change as notes; `pages/address/balance.ts` is the logic, pure but for `loadHistory`, which takes its fetcher. The data is the node's `/address/:address/txs/summary` ([`API.md`](API.md#routes)): 25 rows a page, newest first, each a confirmed transaction's net effect on the address (unconfirmed ones are not listed, so they stay in the page's "Unconfirmed" figure).

- **When it asks.** Only once it is within 300 px of the screen (its summary pages are most of an address page's requests), after the page's own totals and first history page have answered, and only when the totals count a confirmed transaction: an address with no history asks nothing and has no chart, and one whose totals the node refuses as too large asks nothing and says so in a sentence. That check matters: the node can spend over a minute on the first summary page of the largest addresses (95 to 102 s measured on mainnet's largest, whose totals it refuses in tens of milliseconds). The chart's code is preloaded at the same moment, so neither costs an ordinary page view anything before its main content is in. The section holds its height from the first render (the plot, the readout and the caption: three readout lines on a phone), so nothing moves when it arrives.
- **How much.** At most `MAX_PAGES` (8) summary pages, so the newest 200 transactions, every page after the first pinned with `?asof=` to the block the first is stamped with. A history that does not end within them is anchored by one more request, the address's totals as of the same block, and the balance is walked back from that; the header then says "The last 200 of 5 598 confirmed transactions" and the oldest block's change reads "no data" (its other rows may be on a page not loaded). A later page that fails is not an error: the pages already in are anchored the same way. So one page view makes at most 9 of the chart's requests, inside a client's share of the address routes ([`CONFIG.md`](CONFIG.md#address-and-batch-routes)).
- **Live.** The page's refresh on an address change also asks for the newest summary page, once. `advance` joins it to what is loaded by txid and block (taking the page's own rows where they overlap, so a block re-mined at the same height brings its new time) and carries the balance by what is new and what a reorg took away. When the page does not meet the rows loaded (more new transactions than a page holds), that page alone is anchored by the pinned totals: two requests at most, never the whole history again. A change heard while a load is running queues one more update after it, never a second chain.
- **The axis** keeps zero in view for a whole history (it rose from nothing) and fits the data for a partial one, where zero would flatten every step into one line.
- **As of a block** (below) every request, the first summary page too, is pinned to the page's block hash, the line ends at that block's time instead of now, and nothing refreshes it.

### An address as of a block

`/address/:address?at=<height>` shows the address as it stood at that block of the best chain: the node's Esplora address routes take `?asof=<block hash>` ([`API.md`](API.md#routes)) and the server passes it through. `pages/address/Pinned.tsx` is the page, `asof.ts` its pure parsing and checks. The parameter is a height in decimal digits within u32 (`parseHeight`, as `/blocks/:from` reads one), never a hash, so a link reads as a block number and a reload or a shared link reads the same block unless a reorganization replaced it.

- **The block.** The height is resolved first: `/block-height/:height` for its hash, then `/block/:hash` for its time, checked to be that block at that height (`readPinned`). Every read after that carries `?asof=` with that one hash: the totals (`/address/:a`), the first history page (`/txs/chain`, confirmed only), the pages after it (`/txs/chain/:last_seen`), the unspent outputs (`/utxo`) and the balance chart's summary pages and anchor. So the figures, the list, the coins and the chart all agree, and a block mined meanwhile cannot slip into one of them. The tip is never waited for: it is read only when the height is not found, to name the newest block, and when that tip already reaches the height (the block was mined between the two answers) the height is looked up again, up to three times. "Not mined yet" is said only when a tip was read and falls short of the height and one more lookup of the height still misses (that tip may come from the server's one-second cache, from before the block was found), so it is true as of the page's last lookup; a tip that cannot be read, or lookups that keep missing a height the tip reaches, are a failure to look the block up, with Try again. A `404` on any of the chart's pages, the later ones too, is the block leaving the chain, never a reason to draw the pages already in.
- **Nothing live.** The pinned page is a separate body (`AddressPage` keys it by network, address and `at`): it subscribes to no `address:` topic, asks no ledger and polls nothing, and its sections are handed no refresh. The header's block strip and socket status are the shell's and stay live.
- **Each part, pinned.** A band leads the page: "As of block N" linked to the block, its time (UTC, then relative), one sentence saying later blocks and unconfirmed transactions are left out and the page does not update, then "Back to now" (drops `at`), the previous and next block ("Next" is always offered: a step past the tip lands on the message below, which names the newest block then, and the band then offers "Show block N" for it beside "Back to now"), and "Another block" (the block field). The totals show balance, received, sent and transactions as of the block, with no "Unconfirmed" figure (the node's `mempool_stats` is ignored). The chart is pinned as above. The history lists confirmed transactions up to the block; the unspent outputs view lists the coins held at it, its confirmations counted at that block ("Confirmations then"). The lookalike check runs on the pinned rows, so its notice says what the history then held. The live line is replaced by the band; the QR and copy buttons are unchanged.
- **The block field.** Live, "As of a block" at the end of the title's row opens it under the address; pinned, "Another block" opens it in the band, holding the current height. It takes a height (group spaces and commas allowed) or a date or moment read as the command palette reads one (`readDate`), which asks `/api/v1/mining/blocks/timestamp/:t` for the newest block by then (`palette/block-at.ts`, shared with the palette). Either puts the height in the URL as a new history entry, so Back returns to the page before. A date's lookup belongs to the page that asked it: moving to another address or network drops it. Previous, next and Back to now keep `?view=`.
- **Edge cases, each said in words.** `at` that is not a height: the band says so, with the field and Back to now, and no figures. A height above the tip: "Block N has not been mined yet", naming the newest. An address with no confirmed transaction by then: "Not used yet at block N", saying only that no transaction paying or spending it had confirmed by that block, in place of the figures, chart and list; a kept address's empty pinned list says the same. A pinned read answered `404` (the hash left the best chain since the page resolved it): "Block N is no longer on the best chain", with a button that resolves the height again. A large address: one this server has taken for large (more than 10,000 funded outputs, or totals the node took over 5 s to give) is refused by the server's guard without asking the node, and one over the node's cap is refused by the node, both as `too large` and whatever the block, even one where the address had little history ([`API.md`](API.md#very-large-addresses)): the page says only that at a past block this server shows no totals, confirmed transactions or coins for it, because it does not add it up, and makes no claim about the live page. A kept one is refused totals and coins as of any block (`not kept`; the server keeps only its running totals); its history pages answer as of a block only when the server keeps its whole history and the block is among the ledger's last 100 ([`API.md`](API.md#paging-a-kept-history)): the page states both conditions and lists what the server answered. Neither refusal is retried as busy (`isBusy`). A slow or failing node: the resolution or the totals show the error with Try again.

## CSS

- Plain CSS with the tokens in `design/tokens.css`, imported once in `index.tsx`. Never copy a token value; use the custom property.
- Cascade layers, in this order: `reset, base, layout, components, pages`. Shared components write in `@layer components`, pages in `@layer pages`.
- One CSS file per component, next to it, imported by the component. BEM-style names: `block`, `block__part`, `block--variant`. Prefix a page's classes with the page name (`tx-flow`, `block-grid`) so pages never share a class by accident.
- Per-element values (a fee color, a position) are custom properties set through Solid's `style` object, with a value that comes from props or a signal: `style={{ "--swatch": feeColor(rate) }}`. Solid applies those through the CSSOM, which the Content-Security-Policy allows. Never write a `style` string, and never put a literal value in a `style` object: Solid 2's compiler writes the literal entries of an object into the element's `style` attribute in its template, even beside dynamic ones, and the policy blocks that.
- Breakpoints: 1040 px and 640 px ([`DESIGN.md`](DESIGN.md)).

## Theme

Light by default, dark when the OS asks, either one forced by the toggle. A forced choice is stored under `theme` in `localStorage`. Choosing the scheme the OS already shows clears the stored choice, so the page follows the OS again.

The stored theme must apply before first paint, and the Content-Security-Policy forbids inline script. So `index.html` loads `public/boot.js` as a small blocking same-origin script in the head: it sets `data-theme` and `data-network` on `<html>` before the body is drawn. It is fetched alongside the render-blocking stylesheet, so it adds no round trip.

Prose is set in the system font, which needs no download. The web font (Recursive Mono, for hashes, addresses and numeric columns, and the narrow space between digit groups everywhere) is preloaded, and `index.tsx` waits up to 1 s for it before the first render, so text is laid out once. If it is not there in time, the app takes both Recursive faces out of `--font-sans` and `--font-mono` for that page load (read from the tokens, not restated), so a late font never swaps in and reflows text; the next load finds it in the browser's cache. Anything that appears after the first render must not move what is already on screen: reserve its space, or put it where nothing follows it.

## Rules for page builders

1. **Stay in your directory.** A page owns `pages/<page>/` and nothing else. Its only edit outside is the one line in `src/routes.ts`, plus a function in `paths` and types in `lib/esplora.ts` when it needs them; those are append-only.
2. **Shared code changes in its own PR.** `components/`, `lib/`, `shell/` and `styles/` are shared. If a page needs a change there (a new prop, a fix, a new component), make it a small separate PR, or ask whoever is working on the shell. A component used by one page lives in that page's directory until a second page needs it.
3. **Chain data is text.** No `innerHTML`, no markup built from data, no data in `href` or `src` except through `paths` ([`SECURITY.md`](SECURITY.md) rule 14).
4. **No style attributes.** Custom properties through the `style` object, every value dynamic (see "CSS").
5. **Numbers through `lib/format.ts`.** Never `toFixed` a BTC amount or a fee rate in a page. Every amount, rate and size reaches a screen reader with its unit: in a table cell whose unit is in the header, use the components' `unit={false}`, or a `visually-hidden` unit after a number you format yourself.
6. **No layout shift.** Reserve space for what loads later.
7. **Stay in budget.** The shell and the home page together load at most 100 KB of gzipped JavaScript (`bun run size`). Other pages load on demand and should stay small too; a heavy component (the WebGL grid, the charts) loads only on the page that uses it.
8. **Plain HTTP is a real deployment.** A self-hosted explorer is often reached over HTTP at a private address, where browsers hide APIs they keep for secure contexts (`navigator.clipboard`, `crypto.subtle`, `crypto.randomUUID`, service workers). Code that uses one has a fallback that works without it, and a browser test from an insecure origin (`e2e/copy.e2e.ts` shows how); `CopyButton` falls back to the copy command and says when nothing was copied.
9. **Test what has logic.** Pure functions get unit tests next to them. Components can be tested in Vitest's DOM: `mount()` in `components/test-utils.tsx` renders inside a router (`createRouter` with `memoryHistory(url)`) at a given URL. A test that holds code to a speed measures the processor time the code took, with `cost()` in `lib/cost.ts`, never the time that passed: other builds on the machine make a run wait many times as long as it works (a 170 ms read took 2.4 s with every core taken four times over), and a limit on elapsed time then fails for no fault of the code. `cost()` counts the whole process: no other test, as Vitest runs each test file in a process of its own, but Node's background threads with it (garbage collection), so a limit needs room. It measures a synchronous run only, as work after an `await` is not counted, and a test's own timeout is still elapsed time. It is the one place a unit test reaches Node's `process`, which it declares for itself.
10. **Write for Solid 2.** Its migration guide and RFCs are in the solid repository under `documentation/solid-2.0/`; these are the rules that bite in this app:
   - **A write is seen after the flush.** `setX(v); x()` still gives the old value until the update is applied (the next microtask, or `flush()`). Code that writes and then reads in the same turn keeps the value in a plain variable that the signal mirrors (`createBlockFeed`'s list, the pool page's count), or uses the updater form `setX((n) => n + 1)`. `batch` is gone: writes in one turn are applied together.
   - **Effects are split.** `createEffect(() => source(), (value, previous) => { …; return cleanup })`: the first function tracks and only reads, the second does the work untracked and returns its cleanup. `on()` is gone: the first function is the dependency list, and `{ defer: true }` skips the first run. The first function runs when the effect is created, so declare an effect below everything it reads.
   - **`onSettled` replaces `onMount`.** It returns its cleanup; `onCleanup` inside it throws. It runs once, untracked.
   - **No writes from a component body or a memo** (development throws). Write in handlers, effects' second function, `onSettled`, or async callbacks. A value derived from another and also written (the address history's later pages) is a function-form `createSignal((prev) => …)`; `createComputed` is gone.
   - **Boolean attributes are presence.** `true` writes an empty attribute and `false` removes it, so `aria-*` and other true/false attributes take the strings: `aria-busy={loading() ? "true" : "false"}`, `spellcheck="false"`. Attribute names are lowercase (`maxlength`, `tabindex`).
   - **Classes and lists.** `classList` is gone: `class={["base", { "base--on": on() }]}`. `Index` is `<For keyed={false}>`, `splitProps` is `omit`, `Suspense` is `Loading`, `ErrorBoundary` is `Errored`.
   - **Read props in JSX or a memo.** A read at the top of a component body is not tracked and warns in development; wrap a deliberate one-time read in `untrack`.
   - **In tests, flush before you look.** After an event, a timer or a write the test made, call `flush()` before reading signals or the DOM. `FakeSocket` flushes after each message and close, as a browser's task boundary would.

## Accessibility

The bar is WCAG 2.2 AA. What a new page must do:

- **One `h1`, headings in order, the title from `usePageTitle`.** Chain data stays text (rule 3 above), read aloud as text.
- **Every control reachable by Tab in reading order, with the global focus ring.** No positive `tabindex`; never `outline: none` without another ring. Escape closes anything that opens over the page (`components/pop.ts` does it for you). The sticky header never covers focus: `Header.tsx` keeps `--header-h` current for the page's `scroll-padding-top`.
- **A name for every control, table and drawing.** Icon-only buttons take `aria-label`; tables a caption (`DataTable` does it; a column whose rows name themselves takes `hidden` for a header read only aloud); a canvas or chart a text alternative carrying the same figures (`Chart`'s "Show the figures", the list beside `TxGrid`).
- **Live updates said once, politely.** A polite region for a new block, a state change or a copy; never one that changes on every tick.
- **Never colour alone,** and colours only from the tokens: `src/styles/contrast.test.ts` measures every text, mark and surface pair in both themes.
- **Breakpoints in `em`,** so a large text size reaches the narrow layouts. At 18.75em and below, stack what sits two to a row.
- **Motion from the duration tokens,** so reduced motion stops it.

`e2e/a11y.e2e.ts` holds these on every page type: [axe-core](https://github.com/dequelabs/axe-core) (a pinned development dependency, injected by Playwright, never served) in light and dark, a keyboard walk down and back up the page (the skip link first, every control reached, a ring at every stop, none under the header; Option-Tab in WebKit, as in Safari), no movement under reduced motion, Escape on the pop-ups and the search's answer, and the shell and the transaction page at 320 px, at a phone's large text and at 200% text (the text sizes in Chromium only, the one engine a test can set them in). Add a new page type to its list. One axe rule is off, with its reason in the file. axe holds targets at 24 px; `e2e/targets.e2e.ts` holds the design's 44 ([`DESIGN.md`](DESIGN.md#space-shape-and-layout) "Touch") on every page type in `e2e/pages.ts`, at 390 and 320 px on a touch screen, with an exact amount's pop-up open: for every control in sight it measures, from the control's centre, how far a tap still reaches it, by what the browser finds under the finger (`elementFromPoint`), so a neighbour drawn over it counts against it. A link to the same place counts as the same target, as a list's row and its first cell's link are. Give a new small control `.tap` or `.tap-line`.

Checked by hand in November 2026 and not by a test: that no live region speaks on a mempool tick (eight seconds on every live page, mainnet); that the canvas drawings and charts have their text alternatives; the contrast of fades and loading states, which dim content on purpose while it is replaced. A screen reader has not been run; with VoiceOver, check first the home page's block strip and its new-block announcement, a transaction confirming, the search's answer, the exact-amount pop-up, and a chart's slider and figures.

## Checks

Lint, format and type checks are strict, and CI fails on any finding. OXC is the only linter and formatter: never add Biome, ESLint or Prettier.

| Command | Runs | Covers |
|---|---|---|
| `bun run typecheck` | `tsc` on `tsconfig.app.json`, then `tsconfig.node.json` | Everything: the app and its unit tests (browser types only, so app code cannot reach Node's `process` or `Buffer`); browser tests, scripts and configs (Node types) |
| `bun run lint` | `oxlint`, then `oxfmt --check` | What CI's lint step checks |
| `bun run format` | `oxfmt` | Rewrites files in place. `bun run format:check` checks without writing |

- **Lint.** Every `oxlint` category is an error (correctness, suspicious, perf, pedantic, style and restriction), with the TypeScript, unicorn, oxc, import, promise and JSX accessibility plugins, and Vitest's for unit tests. Rules that need types (unawaited promises, promises passed where a callback returns nothing, unsafe `any`) run through `oxlint-tsgolint` on the same tsconfig. Nothing is set to warn. A rule is off in `.oxlintrc.json` only with its reason beside it. An exception for one line is `// oxlint-disable-next-line <rule> -- <why>`; a disable that no longer matches anything fails the check.
- **Format.** `oxfmt` formats everything in `web/` it can parse: TypeScript, JavaScript, JSON, CSS and HTML, at 100 columns. It cannot format `scripts/e2e.sh`.
- **Types.** On top of `strict`: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature` (an index signature is read as `x["key"]`, a reminder it may be missing), `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `allowUnreachableCode` and `allowUnusedLabels` off, `noUncheckedSideEffectImports`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, and `checkJs` for the JavaScript files. Left off: `isolatedDeclarations`, which is for publishing type declarations; and `skipLibCheck` stays on, so dependencies' own type errors are not ours to fix.

## Testing

`bun run test` runs Vitest in a happy-dom document, so logic and components are tested the same way. `bun run size` checks the first load after `bun run build`, and fails on any of three things:

- **JavaScript over 100 KB gzipped:** the scripts `index.html` loads, the home page's chunk, and everything they import statically.
- **More than 10 files on a cold home page:** the document, `boot.js`, the font, the shell's scripts and stylesheet, and the home page's code and styles as the shell's preload list names them. On a slow network each file waits for one of the browser's six connections to a site over HTTP/1.1, so a page that needs 23 small files shows its data about a second later than one that needs 10 ([`PERFORMANCE.md`](PERFORMANCE.md#4-shorten-the-pages-request-chain-on-slow-networks-done)). Raise the number only with a measurement that says the new file is worth its wait.
- **A first stylesheet that does not open with the `reset` layer** (see [below](#chunks)).

### Chunks

How the build splits the code decides how many files a cold page waits for. `vite.config.ts` puts one group, `app`, in front of everything: `index.html` loads a small entry script that only imports it, a `modulepreload` for it and its one stylesheet, all at once.

- **In `app`:** the entry module and the shell it imports (Solid's runtime among it), the live channel and the topics the home page reads (`live.ts`, `blocks-topic.ts`, `projected-topic.ts`), the clock, and the small components most pages use (`Amount`, `DataTable`, `FeeRate`, `Hash`, `SectionHeader`, `Strata`, `Time`), with `Note`, which only the home strip, the Blocks page and the block page use but would otherwise be the cold home page's eleventh and twelfth files (about 1.5 KB), and `QrButton` (about 0.5 KB), which alone was a script and a stylesheet more on the address and node pages' first load; what it opens loads on first use. The search's `ScanButton` comes with the shell that imports it; the scanner and jsQR load on first press. Left to the bundler, the components split by which pages share them into 14 more files of under 1.5 KB each on a cold page.
- **One stylesheet for the shell.** With the entry module in the group, the tokens, the global styles and every style the group imports land in `app`'s stylesheet, the only one `index.html` links. It opens with the layer order from `global.css`; layers are ordered by where each first appears, so a stylesheet linked before it that opened with `@layer components` would make every component lose to the reset. `bun run size` checks it.
- **Everything else stays lazy:** each page with what only it uses, and the heavy parts (the transaction grid, the charts, the audit list, the Lightning pages) only where they are used. A cold home page is 10 files ([`CONFIG.md`](CONFIG.md#per-client-defaults) has every page). The home mempool panel's map and incoming-rate chart (`pages/home/visuals.tsx`, with the grid and the chart) load only once the panel nears the view, after those ten.
- **The cost:** a page loads the whole group, used or not. The transaction page loads `DataTable` and `Strata` (about 2 KB) without drawing them; that is less than the headers of the files it no longer asks for. And the components' styles now come with the shell's stylesheet, which, like the shell's styles before, is not asked for again if it fails to download ([above](#when-a-pages-files-fail-to-load) covers a page's own files).

Add a component to the group only when most pages use it and it would otherwise be a file of its own on their first load.

CI runs typecheck, lint, test, build and size, and the browser tests below ([`CI.md`](CI.md)).

## Browser tests

`bun run e2e` runs the Playwright tests in `web/e2e/` in headless Chromium ([or another engine](#other-engines)) against the real server and a private rbitcoin node on regtest ([`REGTEST.md`](REGTEST.md)). It needs Docker, `python3`, Rust and bun, and does everything else itself: starts the node and builds the known chain, builds the frontend and the server from your checkout, starts the server on a free port with only regtest enabled and its block table in the run's directory (with some mempool history already in it, [below](#adding-a-test)), runs the tests and removes all of it. A second run takes about 10 seconds. Every run uses its own node, port and output directory, so any number can run at once. On a failure it keeps the server log and Playwright's traces and prints where.

Arguments go to Playwright: `bun run e2e tx.e2e.ts`, `bun run e2e -g "deep link"`, `bun run e2e --headed`.

**The server runs with every limit at its production default** ([`CONFIG.md`](CONFIG.md#limits)), so each run also proves that real page loads stay inside them. The tests all come from one address, so each test poses as its own visitor, as its fresh browser context (empty cache, no cookies) is: the server trusts `X-Forwarded-For` from `127.0.0.1` only, and the fixture sends an address of the test's own (`198.18.<worker>.<test>`) on every page, file, API call, WebSocket handshake and `request` call. One address per worker would be one person making a dozen cold loads in seconds, which the block summary route's per-client limit rightly refuses. A test that sets `extraHTTPHeaders` itself must keep that header.

**The headless shell misdraws a canvas under the header.** Playwright's `chromium-headless-shell`, which `bun run e2e` uses, captures a WebGL canvas partly covered by the sticky header with a blank band at its foot as tall as the covered part; full Chromium, headless or not, shows it whole. Seen while building the goggles: a screenshot of the map scrolled under the header is no evidence of a fault.

**A limit that refuses anything fails the run, and says which.** A page or static file answered `429` or `503` ends its test at once with the request named, instead of a later assertion timing out. After the tests, `bun run e2e` fails if the server's log holds any refusal, even of an API call a page retried, and prints them: each line names the route, the limit (`refused`) and the worker's address (`client`).

### Other engines

```sh
E2E_ENGINE=webkit bun run e2e              # or firefox; chromium is the default
E2E_ENGINE=webkit E2E_PHONE=1 bun run e2e  # at a phone's width
```

`E2E_ENGINE` picks Playwright's Chromium, WebKit or Firefox, and `E2E_PHONE=1` a phone: Chromium as a Pixel 7, WebKit as an iPhone 15 (mobile viewport, touch, three device pixels per CSS pixel), and Firefox, which has no mobile emulation, as a 393 × 659 window with touch and three device pixels per CSS pixel. The script downloads the engine into Playwright's own cache on first use; on Linux, `node_modules/.bin/playwright install-deps <engine>` (as root) adds its system libraries once. Pull requests run Chromium at desktop width only; the weekly Browsers workflow runs WebKit and Firefox at both widths ([`CI.md`](CI.md#other-browsers)).

What it proves: the pages work in the WebKit and Gecko engines. What it does not: Playwright builds its own WebKit, so a pass is not Safari on a Mac or an iPhone (other graphics, fonts, network stack and settings), least of all on CI's Linux. Check a change that depends on the engine by hand in Safari too.

Differences found so far (2026-11, Playwright 1.64):

- **A tapped button gets no focus** in WebKit, as in Safari; Chromium gives it focus. A note on a button (`Note`) opens on its click as well as on its focus, so a tap reaches it in both; `sv2.mine.e2e.ts` taps one.
- **Closing a socket that is still connecting** is logged as a failed connection by WebKit and Firefox, not by Chromium. Leaving a page often does that, so `lib/live.ts` closes such a socket once it opens instead.
- **A page whose script failed to download** cannot be loaded again in the same document in WebKit, which keeps the failure ([above](#when-a-pages-files-fail-to-load)). WebKit recovers by reloading the page, Chromium and Firefox in place; `chunks.e2e.ts` covers all three.
- **A character the font lacks** is drawn from another font, chosen differently by each engine: the narrow no-break space that groups digits was 0.15 em in Chromium, 0.12 em in Firefox and 0.05 em in WebKit (`1 293` read as `1293`) until it was added to the subset ([`DESIGN.md`](DESIGN.md#type)). Give any new character a glyph in the subset; `shell.e2e.ts` measures the digit-group gap in every engine. Since prose moved to the system font, a face limited by `unicode-range` supplies that space: Chromium and WebKit use it, while Firefox takes a space from the font of its neighbours (the system font's: 0.10 em on a Mac, 0.20 em in DejaVu Sans on Linux).
- **A font download cut short by leaving the page** is a console error in Firefox ("downloadable font: download failed … status=2152398850", which is `NS_BINDING_ABORTED`), and silent in Chromium and WebKit. Firefox asks for a `unicode-range` face only once a page shows one of its characters, so the digit-gap face used to start downloading after render, and a test that moved on quickly failed about one run in twenty on Linux. The page now loads both faces before its first render (`index.tsx`).
- **A module script runs before a stylesheet linked after it has loaded** in WebKit; Chromium and Firefox wait. The build links ours after the script, so on a slow load the tokens read the empty string and the browser's toolbar took the light colour over a dark page. `index.tsx` waits for the linked stylesheets before it reads tokens and renders; `shell.e2e.ts` delays them to prove it.
- **An SVG of `height: auto` takes its viewBox's ratio** in WebKit even under `contain: size`, so the transaction flow's ribbons held the row at the height they were last drawn at. They are sized by the row instead (`height: 0; min-height: 100%`).
- **A fetch that leaving a page cut off,** and one the page starts while it unloads, is an error of its own in WebKit on Linux ("Fetch API cannot load … due to access control checks"), even when the page caught the rejection. The test fixture holds errors in that wording for our own origin from a page's navigation request, and drops them once the next document starts; a navigation that keeps the page (no content, or aborted) starts none, so they count (`console.e2e.ts`).
- **On Linux** (the Browsers workflow, [`CI.md`](CI.md#other-browsers)), Firefox without a display has no WebGL at all ("Exhausted GL driver options"), so the workflow runs it under Xvfb, where Mesa draws. Firefox there also decides once, at launch, whether to allow WebGL2: only if its GPU probe (`gfxtest`) answers within 4 s. On a busy runner it sometimes did not, and that browser refused WebGL2 for its whole life ("AllowWebgl2:false restricts context creation on this system"), so the first grid tests it ran found the page's no-WebGL2 stand-in, correctly shown, and timed out; the worker Playwright started after the failure worked. The tests launch Firefox with `webgl.force-enabled`, which skips that check. A visitor's Firefox that refuses the same way gets the fee layers and the note that the map needs WebGL2. WebKit there shows a WebGL frame drawn without antialiasing only once the next frame is drawn, so the grid draws its last frame twice; otherwise a single frame (a restored context, a resize, a theme switch) never appears.
- **Safari's Tab** reaches only form fields unless the reader has turned on "Press Tab to highlight each item"; Option-Tab reaches the skip link and every link. Playwright's WebKit does the same.
- **WebKit shows a JSON reply** (`/healthz`, an API route opened as a page) in a viewer the Content-Security-Policy refuses, which logs a violation that is not the site's.
- Same in all three: `ws:` and `wss:` to the page's own host under `default-src 'self'`, the `Origin` check on `/app/ws`, WebGL2 and the page without it, the charts' pointer, touch and keyboard read-outs, reduced motion. Numbers and dates are formatted by our own code, not `Intl`, so they read the same everywhere.

Write browser tests so they hold in every engine:

- **Read a screenshot at the device's scale.** Desktop Safari has two device pixels per CSS pixel and the iPhone three: divide by the ratio, never assume 1 (`grid.e2e.ts`).
- **CSP violations are reported by the page,** through `securitypolicyviolation`, since each engine words its console message differently. In WebKit, every Playwright screenshot adds a style the policy refuses, reported against the document rather than an element; the fixture names that one and drops it. `csp.e2e.ts` proves a style of the site's still fails its test, screenshot or not.
- **A test that depends on width checks it** (`page.viewportSize()`), as the home page's test does for the note a phone hides.
- **Wait for the page's frames, not a clock.** WebKit at phone width on a busy runner went over 3 s without a frame after a resize, so a check that gave the page 3 s to fit its tables failed. `tablesFit` (`e2e/rows.ts`) waits until two frames pass with no resize of what the tables watch, then checks once. Those frames are slow there: just after a page loads, WebKit at a phone's three device pixels per CSS pixel takes 0.3 to 1.3 s a frame at 720 px on CI's runner, so each page's wait costs 1 to 3 s. A test that loads many pages and checks each would run past Playwright's 30 s, so such tests take a few pages each (`tables.e2e.ts`, `lightning.e2e.ts`).
- **Phone screenshots for a UI change come from WebKit** as an iPhone, besides Chromium: the owner's first device is a phone.

### Other systems' fonts

Prose is set in the reader's system font, and most readers are not on a Mac ([`DESIGN.md`](DESIGN.md#type)). The browser tests can set prose in a stand-in for another system's font instead, on any machine, with nothing installed and no font file in the product: `e2e/fixtures.ts` registers local faces (`FontFace` with `local()`) before the app runs and points `--font-sans` at them, keeping "Recursive Gap" first as the real stack does. A run whose machine has none of a stand-in's faces fails, rather than measure in the wrong font.

| Stand-in | Faces, the first this system has | Stands for |
|---|---|---|
| `wide` | DejaVu Sans (Linux), Verdana (Mac, Windows) | DejaVu Sans, Linux's usual default and the widest measured |
| `narrow` | Liberation Sans (Linux), Arial (Mac, Windows) | Roboto, Cantarell, Segoe UI and other narrow faces |

Widths of 20 of the site's own strings ("Fees waiting", "0.0000426 BTC", "Lowest accepted", the section names, a fee rate, a sentence), 16 px, in Chromium, against San Francisco; the Linux fonts measured in an Ubuntu 24.04 container (2026-11):

| Font | Regular | Bold (600) |
|---|---|---|
| DejaVu Sans | +10.0% | +18.6% |
| Verdana (the `wide` stand-in on a Mac) | +10.2%, each string within −1.4 to +3.2% of DejaVu's | +18.4%, within −1.7 to +4.9% |
| Noto Sans | +2.8% | +4.5% |
| Roboto | −2.1% | −5.3% |
| Cantarell | −2.2% | −3.6% |
| Liberation Sans, Arial (`narrow`) | −2.7% | −0.2% |

Segoe UI, Windows' default, could not be measured here (it is not free to install); its published metrics put it among the narrow faces.

```sh
E2E_PROSE=wide bun run e2e tables.e2e.ts amounts.e2e.ts shell.e2e.ts   # the rule tests in a stand-in
E2E_SWEEP=1 bun run e2e fonts.e2e.ts                                   # the whole sweep, wide
E2E_SWEEP=1 E2E_PROSE=narrow bun run e2e fonts.e2e.ts                  # or narrow, or system
```

`fonts.e2e.ts` loads every page type once and resizes it through the widths, checking at each that no text runs into other text, nothing is cut, on any edge, by a box that scrolling cannot move (a cut name or hash keeps its whole in its title, and a short form such as `mwLW3XD…UAuat` never loses what follows its "…"), no control's label wraps when it has room to grow, no figure wraps or leaves its field (`amountsIntact`), every table fits or shows that it scrolls (`tablesFit`), and the page is no wider than the window (`layoutFaults` in `e2e/layout.ts`). It lists every fault of a run at once. With `E2E_SWEEP=1` it takes the design's widths, 640 and 1040 either side, and every 40 px from 320 to 1440, each in both schemes: about 5 s a page. Pull requests run it in the wide stand-in at the widths where it found faults, 320, 400, 641 and 1100 px, one scheme each: about half a second a page.

To see the real fonts rather than a stand-in, run the same tests in a Linux container with `fonts-dejavu-core` and `fonts-noto-core` and Playwright 1.64.1's Chromium, with `E2E_PROSE=system` and `E2E_BASE_URL` pointing at a `bun run e2e`-style server the container can reach. On 2026-11-13, in that container (Ubuntu 24.04, Chromium), the whole sweep on the build before the fixes failed in all ten places the `wide` stand-in found on a Mac with DejaVu Sans as the system font, and in six of them with Noto Sans; after the fixes it passed with both.

### Adding a test

Put it beside the others as `web/e2e/<page>.e2e.ts` (the `.e2e.ts` suffix keeps Vitest away from it), and import from `./fixtures`, never from `@playwright/test`:

```ts
import { chain, expect, test } from "./fixtures";

test("a block page shows its height", async ({ page }) => {
  await page.goto(`/regtest/block/${chain.blocks[106]}`);
  await expect(page.getByRole("heading", { level: 1 })).toContainText("106");
});
```

- **Pages are under `/regtest/`.** Only regtest is enabled, so the root is a 404.
- **`chain`** in `e2e/fixtures.ts` is the scenario's manifest: tip, block hashes, txids and addresses of every script type. They are the same on every run.
- **Every test fails on a console error, an uncaught exception or a Content-Security-Policy violation** on any page it opens. The fixture does this by itself. If your test causes an error on purpose, such as a request that is meant to 404, name it: `test.use({ consoleErrorsAllowed: [/status of 404/] })`. A CSP violation cannot be allowed.
- **Find elements by role and text,** as a reader would (`getByRole`, `getByText`), not by class names.
- **Tests share one node and run in parallel, so only `*.mine.e2e.ts` files mine.** A new block changes the tip every other test reads. Playwright runs those files in a separate `mines` project that starts after every other test has finished and runs one test at a time; only there does the `mine(n)` fixture work (it returns the new block hashes). Anything else that changes the chain belongs there too. The broadcast test in `api.e2e.ts` adds one transaction to the mempool, so do not assert the mempool's exact size.

  ```ts
  test("a new block lands without a reload", async ({ page, mine }) => {
    await page.goto("/regtest/");
    const [hash] = await mine(1);
    const strip = page.getByRole("list", { name: "Mined blocks, newest first" });
    await expect(strip.getByRole("link").first()).toHaveAttribute("href", `/regtest/block/${hash}`);
  });
  ```

- **Hostile chain data.** `hostile.mine.e2e.ts` puts markup, a `javascript:` URL, bidi overrides, ANSI escapes and NUL on the chain (`regtest.py hostile`: OP_RETURN outputs, a taproot reveal of three inscriptions (HTML, JSON and an SVG with a script) and a hand-built coinbase tag) and checks the transaction, block and address pages show them as visible, inert text on the cards, in the inspector and in the block's tag: no injected element or event attribute, no dialog, no unexpected link scheme, and the SVG named by its type and size, never drawn. A new page that shows chain data belongs in it.
- **Wait on the page's own bounds, by name.** The projected blocks can trail the node by up to `PROJECTION_LAG_MS` (in `e2e/fixtures.ts`, with its reasoning): a new transaction until the tracker's next cycle and the topic's next send, a new block until its projection, which follows the `block` message at once unless the node is slow to serve the block; the next block's page then holds its notice for up to `FOUND_WAIT_MS` (`src/pages/projected/state.ts`). Import those constants rather than writing a timeout, so the test and the page cannot drift apart. Each wait ends as soon as the page catches up. Before a mining test starts, the `mine` fixture waits until the server's `blocks` and `projected` topics both sit on the node's tip, at most `PROJECTION_LAG_MS`, and fails naming what lagged; otherwise blocks an earlier test mined would arrive together with this test's.
- **Mempool history is stored before the server starts.** The server records its first minute 60 to 120 s after it starts, so `bun run e2e` first writes 15 minutes an hour old, with a five-minute gap, through the sampler's own writer (`crates/engine/src/bin/history_seed.rs`), and `mempool.e2e.ts` checks the page shows exactly those. Never wait for a live minute in a browser test: the sampler's timing, skipped minutes and roll-ups are proved by the engine's tests on a paused clock (`crates/engine/src/history/tests.rs`), and the page's refetch at each minute by its unit tests.
- **Pages regtest cannot fill** (Lightning is off on regtest) are driven from recorded answers: `lightning.e2e.ts` serves `/regtest/app/lightning/…` with `page.route` from mainnet answers in `fixtures/lightning/app/`, so the built pages are drawn from real data with no test-only route on the server. Its own status route still answers `off`, which the same file checks.
- **Keep the suite fast.** Browser tests cover what only a browser can show: that the page renders real data, links work and nothing errors. Logic belongs in unit tests.
